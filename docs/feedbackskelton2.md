# LitTraceQA 論文骨組みへの査読者観点フィードバック

## 前提と総評

以下は、**システムの実装・数値の正しさを精査するのではなく、初見の査読者が論文としてどう理解し、どこで不安を抱くか**という観点からのコメントです。現時点の原稿は、失敗分析から設計を導く姿勢が非常に一貫しています。とくに、質問文だけでは直接指せない論文を論文間近傍で補うという問題設定と、`multi_paper` で「1本目の後に続かない」という診断は、論文の核として十分に魅力があります。

一方で、現状は**良質な開発ノート／設計根拠集**に近く、査読論文としては「何が新しい中心アイデアなのか」「完全構成は本当に効くのか」「公式評価に対して何を主張するのか」を短時間で把握しにくい構成です。査読者に一文で持ち帰ってほしい主張を、次の程度まで絞るのがよいと思います。

> **質問に直接言及されない関連 gold 論文が存在する科学論文 QA では、質問起点の検索だけでなく、初期候補からの論文間展開を順位融合することで、特に複数論文問題の候補回収を改善できる。**

この主張を中心に据え、論文単位融合・Seed Expansion・reranker 融合は「この主張を成立させるための補助的だが合理的な設計」として整理すると、読み手の負荷が大きく下がります。

### 1. 完全構成の主表は、論文全体の「契約書」です

現状では、§3.3 のランキング B の対照は非常に強いです。同一の検索結果から候補列だけを組み直すため、LLM のばらつきが混ざらず、`multi_paper` における改善の解釈も明快です。しかし、その数値は §3.1 がいう「論文単位融合・クエリ拡張・順位融合を無効にした構成」の上で測られています。したがって初見の査読者は、次の疑問を持ちます。

> 「ランキング B が効くことは分かった。しかし、**最終システム上でも**同じ効果があり、追加した3部品と両立するのか。」

この疑問は限界節で正直に書くだけでは解消しません。主結果は、以下のように**完全構成を基準にした表**にしてください。

| 完全構成 − ランキング B |  |  |  |  | 論文間展開の寄与 |
| 完全構成 − 論文単位融合 |  |  |  |  | 融合単位の寄与 |

すべての組合せを網羅する必要はありません。ただし、少なくとも**完全構成対完全構成−B**、および最終主張に関わる部品の単独除去は必要です。§3.4 のように複数変更を一度に入れる比較は開発上は自然でも、論文上はどの要素が寄与したかを分離できません。

### 2. `ecr` は有用だが、使い方を一段慎重にする

`evidence_candidate_recall@k` は、検索器の改善を「質問と根拠の対応がある gold に限定して」診断するという意味で合理的です。むしろ、このデータセットの評価注釈の不整合／多層性を可視化する重要な分析になりえます。

ただし、査読者は次の二点を気にします。第一に、evidence の有無が原理的な到達可能性と同義なのか。第二に、公式 gold を除外することでスコアが高く見えていないか、です。本文では `ecr` を改善の主たる根拠に使うのではなく、次の位置付けにすると安全です。

> **公式 candidate recall を主評価とし、ecr は「質問起点の証拠検索に対する設計上の効果」を分解して読むための診断指標とする。**

さらに、指標の定義を §1.2 と §3.1 に分散させず、実験設定に以下を1表でまとめてください。

| 指標 | 分母 | 集約 | 目的 | 報告位置 |
| --- | --- | --- | --- | --- |
| 公式 candidate recall@k | 全 gold 論文 | macro / micro を明記 | コンペ仕様に沿った最終評価 | 主表の左端 |
| ecr@k | evidence が結び付く gold のみ | 分母が空のクエリの扱いを明記 | 検索設計の診断 | 主表の補助列 |
| All-Gold@k | クエリ | official / evidence-annotated を明記 | 全論文を揃える難しさ | 補助表 |
| evidence precision / recall / F1 | evidence 注釈 | 照合規則を明記 | 根拠抽出の品質 | 独立表 |

原稿内には `micro` と `macro` の記述が併存しています。§1.3 や §3.2 の個別分析と、§3.1 の最終報告で集約方法が異なるなら、それ自体は問題ありません。ただし、**各表の表題・脚注に必ず集約単位を明記**してください。これは査読者が最も簡単に不整合を疑う箇所です。

## 初見では分かりにくい、または誤解されやすい点

### 3. 「ピア gold」の命名と因果表現を弱める

§1.2 の発見は面白い一方で、「evidence がない」「質問文が名指ししない」「したがってベクトル化しても来ない」「検索器の性能不足ではない」が連続するため、主張が少し強く読めます。55件の検証集合の観察から一般的・原理的な不可能性まで主張しているように見えるからです。

次のように限定すると、むしろ研究として正確で強くなります。

| 現在の読み方になりやすい表現 | 推奨する方向 |
| --- | --- |
| 「原理的に取れない29本」 | 「質問文だけを入力とする本検証条件では、直接回収が難しい29本」 |
| 「埋め込みを大きくしても縮まらない」 | 「本分析では、質問起点のランキングがこの群に対して大きく低下した」 |
| 「reranker は…必ず下げる」 | 「質問適合性のみを主に最適化する reranker は、この群を下げるリスクがある」 |
| 「検索器の性能不足ではない」 | 「検索器の能力だけでなく、質問と gold の対応関係に由来する要因がある」 |

また、`peer gold` は直感的ですが、まずはデータ上の定義である **「evidence 未注釈 gold」** を導入し、本文の誤り分析で「内容を確認した範囲では、同一トピックの周辺論文として機能している」と説明するほうが安全です。タスク主催者の注釈仕様が「関連論文も gold にする」と明示しているなら、その仕様を直接引用して定義してください。明示されていないなら、少なくとも数件の手動監査結果を短い表で置くと説得力が増します。

### 4. Reader の範囲は、現状の説明より狭くありません

冒頭では「Reader は別チームの担当で、この文書では扱わない」とあります。しかし §2.3.2 の GPT-5.4 は、候補を読んで `paper_ids` と evidence を返し、その `paper_ids` はランキング B の起点になります。つまり**回答生成はしなくても、読解判定は retrieval policy を変える**構成です。

これは問題ではありません。むしろ、検索と検証を交互に行う設計として興味深い点です。ただし、次のように役割を分けて明示してください。

> 本稿の対象は候補論文検索および evidence verification であり、最終回答の生成・提出論文の選択は扱わない。verification module は evidence を返すと同時に、次の論文間展開の anchor を提供する retrieval controller としてのみ用いる。

全体図でも、最終 Reader と verification module を同じ「読解」と呼ばないほうがよいです。前者が別チームの回答生成器なら、後者は `Evidence Verifier` あるいは `Retrieval Controller` と呼ぶと境界が明瞭になります。

### 5. 「テストセットでの性能」という見出しは避ける

§3.8 では gold がないと明示されているので、性能を測れていないこと自体は適切に認識されています。ただし「Test set での性能」という節題は、初見の読者に公式スコアまたは正解に基づく評価を期待させます。

この節は、**「Unlabeled test inputs における出力健全性と構成間の挙動」**などに改題するのがよいです。候補が50本埋まる、ID／タイトルが解決できる、evidence が出る、といった結果は提出品質の sanity check として価値があります。しかし、候補列の Jaccard が低いことは「どちらがよいか」を示しません。検証セットと問題形式の分布差もあるため、ここから test での優劣を推論しない書き方を徹底してください。

## 何を本文に残し、何を付録へ移すか

現状はすべての設計判断を「設定→結果→解釈→設計」の四段で記述しています。これは開発記録として優れていますが、論文本文では同じ型の反復が続き、重要度の差が消えます。本文は**再現に必要な仕様**ではなく、**主張を検証するために必要な根拠**を優先してください。

| 内容 | 推奨配置 | 理由 |
| --- | --- | --- |
| ランキング B の問題設定、3種類の近傍、A/B 融合 | **本文** | 本稿の中心的な新規性・主張に直結する |
| `multi_paper` で2本目以降が沈む分析 | **本文、図1枚** | B を導入する最も直感的な動機になる |
| 質問起点 A と B の完全構成上の対照実験 | **本文、主表** | 中心主張の直接証拠 |
| 論文単位融合と「table は順位付けから除外、読解には保持」の洞察 | **本文では短く** | 実務的で良い洞察。ただし中心主張を上回らせない |
| Seed Expansion の AlphaPO 単一事例 | **誤り分析または付録** | 1例は直感補助にはなるが、Introduction の核にはしにくい |
| `1e-9` オフセットの安全性計算、score 書戻しの実装事情 | **付録** | 再現性には重要だが、主張理解に不要 |
| Web 検索演算子が何%出たか、再分解の本数分布 | **付録または短い実装注記** | プロンプト設計の細部であり、主結果ではない |
| 採用しなかった機構の全一覧 | **付録** | 本文では1段落で「開発中に検討した」程度で十分 |
| 未追試の参照実装の数値 | **原則削除、残すなら関連研究** | 査読者は検証不能な数値を中心根拠として受け取らない。自分たちの結果だけで議論を閉じるべき |
| 全パラメータ一覧 | **付録** | 再現性に有益。本文には主要値だけを残す |

とくに §1.5、§2.2.5、§2.2.7 に現れる「同じ論文の複数チャンクが票を持つ歪み」の説明は、同一の洞察が複数回登場しています。Introduction では一段落と図で問題を示し、Method では定義だけを示し、Results でアブレーションを示す、というように**役割ごとに一度だけ**説明すると読みやすくなります。

## 推奨する論文構成

以下は、現在の材料を大きく捨てずに、査読者が追いやすい順序へ並べ替える案です。

### 1. Introduction

冒頭でタスクの入力・出力・対象範囲を形式的に定義します。次に、最重要の診断を一つだけ置きます。すなわち、`multi_paper` 問題では質問起点検索が第1論文を見つけても第2、第3論文を取り逃がしやすく、gold には質問に直接現れない関連論文も含まれる、という観察です。その後に、**論文間展開を導入する**という解法、完全構成の主要結果、三つ程度に絞った貢献を提示します。

Introduction に §1.2〜§1.7 の全分析を入れる必要はありません。いまの §1.8 は良いまとめですが、「設計方針」ではなく「貢献」として短く書き直すと機能します。

### 2. Related Work

現状の骨組みには関連研究がありません。コンペ論文であっても、科学文献検索、dense/sparse hybrid retrieval、pseudo relevance feedback、citation／bibliographic coupling、rank fusion、iterative retrieval のどれと本手法が違うのかを短く示したほうがよいです。

重要なのは、既存手法を網羅することではなく、**質問→文書の関連性だけでなく、初期候補→周辺論文の関係を使う理由**を先行研究の中で位置付けることです。「既存の文献検索の組合せ」に見えるリスクを下げられます。

### 3. Method

全体図は非常に有用です。ただし、現在の ASCII 図には検索、再検索、reranker、LLM、A/B 融合、チャンクプールが一度に詰め込まれており、初見では時間方向が追いにくいです。図を次の三層に分けるとよいです。

1. **質問起点ランキング A**：複数索引、論文単位融合、Seed Expansion、reranker 融合。

1. **Evidence verification と反復**：evidence verifier が停止条件と追加 anchor を返す。

1. **論文間ランキング B と最終融合**：anchor から三つの近傍を取得し、A と融合する。

Method 本文にはアルゴリズム、入力出力、主要ハイパーパラメータ、計算量を残します。一方で、なぜ `k=10` なのか、なぜ `pool_k=200` なのかといった開発経緯の詳細は、実験または付録へ移してください。Method が「設計を説明する章」から「実験ログを読む章」に見えないようにすることが大切です。

### 4. Experimental Setup

§3.1 を独立節として強化してください。査読者が最初に確認したいのは、データ分割、公式の評価、gold と evidence の関係、ベースライン、ハイパーパラメータ選択、LLM の再現性、計算資源です。

特に次の情報は明記が必要です。

| 項目 | 最低限書くべきこと |
| --- | --- |
| データの役割 | 55問は開発・チューニング・最終評価のどれに使ったか。71問は提出対象であり、gold なしであること |
| 評価 | 公式指標、ecr、evidence F1 の厳密な定義、macro/micro、空分母の扱い |
| モデル | モデル名、バージョン／デプロイ名、温度・seed・推論設定、失敗時の再試行またはフォールバック |
| ベースライン | どの構成を比較するか。可能ならタスクの公開ベースラインや単純な強い hybrid retrieval を含める |
| 計算コスト | 1問あたりの平均・最大 LLM 呼出し、平均 wall-clock time、GPU／CPU、メモリ。最大値だけでなく実測平均も示す |
| 選択手順 | どのパラメータを55問で選んだか。探索回数または候補数。最終構成をいつ固定したか |

### 5. Results and Analysis

結果は次の順が最も読みやすいです。まず完全構成の主表を置く。次に、完全構成上のランキング B アブレーションで中心主張を示す。続いて、論文単位融合、Seed Expansion、reranker 融合を「補助的な設計選択」として短い表にまとめます。evidence の結果は独立に示し、最後に代表例を含む誤り分析を置きます。

§3.3 は現在でも最も説得力のある節です。主表の次に置いて問題ありません。ただし「single が不変」の説明は、設計上そうなることが分かるため、本文では一段落に圧縮し、詳細な微視的分析は付録へ移してよいです。

### 6. Limitations and Conclusion

現状の §3.9 は率直でよいです。ただし、「完全構成でのアブレーションではない」という点は limitation に隠すのではなく、主実験で解消すべき項目です。limitation には、gold なし test、入力形式の分布差、evidence verifier の失敗、LLM の再現性、限られた開発集合といった、解消しきれない制約を残してください。

| §2.2.9 | 中心的な節。良い | A/B の入力、rank の範囲、複数 anchor の集約規則、B が空の場合を簡潔に明確化 |
| §2.3.2 | Reader 対象外との境界が曖昧 | Evidence verifier として命名・位置付けを変更。出力フォーマットの失敗率とフォールバックを示す |
| §3.2 | 「結果待ち」のままでは論文化できない | 完全構成結果と強い比較を埋めてから、ここを主結果節にする |
| §3.7 | evidence F1 が低いことを隠していないのは良い | 評価照合の妥当性、0件時の挙動、candidate recall と evidence quality の関係を明示 |
| §3.8 | gold がないのに「性能」と読める | 見出しを sanity check／挙動分析に変更し、優劣の含意を避ける |
| §4 | 誠実だが本文の焦点を散らす | 付録へ移す。本文には設計選択の原則を短く残す |

## 書かないほうがよいこと、または書き方を変えたほうがよいこと

### 内部の開発経緯を、すべて本文に出さない

「以前はこうだった」「この事故が起きた」「実装上すべての下流が score を並べ替えた」といった説明は、再現実装を読む人には有益です。しかし、査読者が知りたいのは、最終手法が何で、なぜ妥当で、実際に効くかです。開発の試行錯誤は、重要な失敗モードを一つか二つだけ残すのがよいです。

とくに `1e-9` のオフセット、擬似 chunk ID、Web 演算子の混入率、各種の「事故」の詳細は、付録に置けば再現性を損なわず、本文を強くできます。

### 未追試の他実装の数値を、設計根拠にしない

原稿では未追試であることを明記しており、姿勢は正しいです。ただし、数値を載せた時点で読者には補助証拠として作用します。査読者によっては「比較可能性がない数値をなぜ載せるのか」と感じます。

自分たちの結果で同じ主張ができるなら、数値は削り、関連研究で「類似の観察が報告されている」程度にとどめるのが最も安全です。残す場合も、表や主張の近くではなく、脚注または付録に置いてください。

### 強い断定を避ける

「必ず」「原理的に」「性能不足ではない」「保証できる」は、数学的な証明または広い条件での検証がない限り避けたほうが安全です。実装に関する局所的な不変条件なら保証と書けますが、検索・モデル挙動については「本検証集合では」「この構成では」と範囲を限定してください。限定は弱さではなく、査読者に信頼感を与えます。

## 逆に、積極的に強調すべき良い点

第一に、**データセットの評価構造を観察し、それに応じて retrieval の単位を変えた**という点です。チャンクで索引しながら論文で評価する不整合、表チャンクが検索順位ではノイズになりうる一方 evidence には重要であること、という分析は実務的な洞察として強いです。

第二に、**ランキング B の対照の作り方**です。同じ検索結果から候補列だけを再構成する比較は、LLM の非決定性を含まないため、他のアブレーションより因果解釈が明快です。この設計上の強みを、表の脚注と本文で明確に言ってください。

第三に、限界を隠していない点です。evidence の不安定性、test に gold がないこと、小さな検証集合、完全構成でないアブレーションという弱点を自覚できています。これを単なる「Limitations」の列挙にせず、主実験を強化して残る制約だけに絞れば、誠実さが大きな長所になります。

## 結び

現状の材料には、単なる「検索器をいろいろ足したシステム」ではなく、**候補集合に含まれる論文間の関係を使わないと、多論文根拠の回収が詰まる**という明確な研究上のメッセージがあります。最も重要なのは、設計上の細かな正しさをさらに説明することではなく、完全構成の評価を揃え、その一つのメッセージへ本文の情報量を集中させることです。

その整理ができれば、今ある丁寧な失敗分析は、冗長な開発経緯ではなく「なぜこの設計が必要だったのか」を支える強い証拠として機能します。
