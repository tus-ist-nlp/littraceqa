LitTraceQA 改稿版5：再レビュー

総評

今回の改稿では、前回まで残っていた最大のスコープ上の不整合、すなわち「evidence を成果物として掲げながら evidence の品質を評価しない」という問題が、本稿の成果物を候補論文50本の順位列に限定することでほぼ解消されています。Evidence Verifier は、最終回答や根拠提示を担うモジュールではなく、反復停止と論文間展開を制御する内部信号として定義されました。この整理は非常に良いです。

また、候補50本を下流が順位で切らず候補集合として利用する、という実運用上の前提をIntroductionへ移した点も重要です。これにより、順位付き出力を返しながら最終構成の選択では @50 の被覆を重視する理由が、Resultsに到達する前から理解できるようになりました。さらに、疑似コードにはフィルタ後の切詰め、最大3周での停止、前周の verifier 判定の保持、初回失敗時の再分解、擬似chunkの扱いが追加され、再現性は明確に改善しています。

現時点で、初見の査読者が最も強く止まるのは、ランキング B の内部融合が本文・図・疑似コードで同じアルゴリズムとして書かれていない点です。ここは単なる説明不足ではなく、候補の順位を変えうる手法定義の不整合です。最優先で正確に統一してください。

最優先：ランキング B の定義を完全に統一する

現在の不整合

§3.1の図と§3.4は、各anchorから得る SPECTER2・書誌結合・全文MLT の近傍ランキングを、RRF(k=60) で融合してランキング B を作る、と説明しています。これは「複数の近さに支持された論文を上げる」設計です。

しかし、疑似コードでは次のようになっています。

Plain Text


pools ← interleave([neighbors(a, n=100) for a in anchors for s in 3 sources])
B ← [anchors] + [p for p in pools if p ∉ anchors]



この記述には三つの問題があります。第一に、neighbors(a, n=100) に source s が渡されておらず、どの近傍を取得するのか分かりません。第二に、interleave は順位列を交互に並べる操作であり、本文が主張する B内部のRRF融合 ではありません。第三に、複数anchor・複数sourceから同じ論文が現れたとき、その重複支持をスコアへどう反映するかが定義されません。

これは結果を変えうるため、投稿版では必ず実装と一致する一つの定義にしてください。

書き方の例

実装が「各anchorについて自己論文を1票、各sourceの近傍を1票として、すべてをRRFする」設計なら、以下のように書けます。

Plain Text


B_lists ← []
for a in unique(anchors):
    B_lists.append([a])                 # anchor 自身を B に残すための1票
    for s in {SPECTER2, Biblio, MLT}:
        B_lists.append(neighbors_s(a, 100))
B ← RRF(B_lists, k=60)



この定義では、各anchorは一度だけ自己支持を得ます。同じ論文が複数anchorまたは複数sourceの近傍に出るなら、複数のRRF項を得ます。これは「複数の関係から支持された論文を上げる」という§3.4の説明と整合します。

ただし、実装が「まずanchorごとに3sourceを融合し、その後anchor間を融合する」形なら、上の例は違います。その場合は二段のRRFとして正確に書く必要があります。重要なのは、interleaveという未定義の順位列操作で済ませず、実装上の融合単位・重複・重みを明記することです。

Methodに残る重要な明確化点

1. Seed Expansionの融合単位を一文だけ補う

通常検索では3索引を論文単位RRFします。Seed Expansionでは runs + runs2 を一括で paper_rrf に渡しています。この疑似コードは、初回の3索引と拡張後の3索引を、合計6本の順位リストとして等重みRRFすると読めます。

それが意図なら、その一文を §3.2.3 に足してください。もし「初回と拡張後をそれぞれ3索引で融合し、その二つのランキングをさらに融合する」実装なら、疑似コードを二段に直してください。両者は順位への寄与が異なるため、初見の読者には曖昧なままにしないほうがよいです。

2. 未使用の evidence_chunk_ids を返させる必要性を検討する

retrieval-only にスコープを絞ったことで、evidence_chunk_ids は本稿の出力でも、反復停止でも、anchor選択でも使われません。現状のままでも論理矛盾はありませんが、査読者は「なぜLLMに使わないフィールドを生成させるのか」と疑問に思うかもしれません。

運用ログや後段チームとのインターフェースのために必要なら、次のように明記すれば十分です。


evidence_chunk_ids は下流チームとの共有ログにのみ保持し、本稿の検索経路および評価には用いない。

そうでなければ、Verifierの構造化出力から外すことも検討できます。未使用フィールドを減らせば、出力形式の失敗率を下げられる可能性があります。

3. Verifierに渡せない論文の処理を明記する

擬似chunkの扱いは大きく改善されましたが、Verifier入力の説明にはまだ1つだけ隙間があります。論文単位BM25で順位が上がった論文が実チャンクを持たない場合、top20論文に選ばれてもVerifierへ渡す本文がありません。

あるいは、Verifier-selected papers と一貫して呼んでもよいです。これは小さな表現修正ですが、評価対象外のモジュールに強い意味を与えないために有効です。

論旨・構成についてのコメント

1. retrieval-only化は正しいが、Evidence Verifier の名称を一言補足するとよい

§1.1は「本稿はretrievalに閉じている」と明快です。一方で Evidence Verifier という名称は、根拠の正確性を評価する研究だと連想させる可能性があります。初出時に、次の一文を加えると誤解を防げます。


本稿での Evidence Verifier は、最終的な根拠品質を保証するモジュールではなく、候補が質問を支持しうるかを判定して検索を制御する内部モジュールである。

これにより、evidence qualityを評価しないという§4.2の立場がより自然になります。

2. Base構成の名称を、表ではさらに具体化する

Base 構成 は以前より良くなりましたが、表だけを読むとランキング B を含むのかが一瞬分かりません。表題・凡例では、たとえば Base A+B (without three retrieval refinements) のように書くと、Aのみとの混同を避けられます。

3. 作業原稿用の注意書きは、投稿版で必ず消す

冒頭に「これは作業原稿である」と明記したのは、現段階の共同作業には便利です。ただし投稿版では、次をすべて消すか通常の学術記述へ置き換える必要があります。

実験と主張の整合性について

実験値そのものではなく、結果の位置付けについては今回の改稿で非常に良くなりました。Base構成上の対照であること、最終構成で同じ対照は未実施であること、外部ベースラインが未測定であることを明示しています。この透明性は維持してください。

ただし最終投稿版では、中心主張の証拠となる実験はLimitationsに「必要」と書くだけでなく、可能な限りResultsで完結させるべきです。とくに最終構成上のAのみ対A+Bは、論文の中核に関わります。もし実装ログが残らず追加測定が難しいなら、最終稿の中心主張を 「Base構成におけるランキング B の効果」 と限定するほうが、主張と証拠の対応は正確です。

結論

今回の改稿で、前回指摘したevidenceの責務範囲、反復処理の状態管理、最大呼出し数、フィルタ後の件数、擬似chunkの扱いは、いずれもかなり改善しました。候補論文検索に限定するスコープも自然です。

残る本質的な修正は一つです。ランキング B が「3種類の近傍と複数anchorをどう融合するランキングなのか」を、実装どおりに一意に定義してください。ここが揃えば、初見の査読者がMethodで立ち止まる最大の理由はほぼ取り除けます。
