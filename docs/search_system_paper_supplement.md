## Claim

> 質問文が直接言及しない関連 gold 論文を含む科学論文 QA では、質問を起点とする検索に加えて、初期候補から論文間展開を行い、その順位を融合することで、特に複数論文問題における候補論文の回収を改善できる。

以下では、Introduction、Related Work、Method、Experimental Setup、Results、Limitations、Conclusion の順に原稿素材を示す。詳細な仕様および開発時の設計判断は付録に記載する。

# 1. Introduction

## 1.1 Task and Scope

質問 `q` に対して、回答の根拠となる論文を27,487本からなるコーパスから同定し、その根拠に基づいて回答を生成する。

**本稿は、検索モジュールと読解モジュールの2つからなるシステムを扱う。**

| Module | Input | Output | Section |
| --- | --- | --- | --- |
| **検索**（Retriever） | 質問文 | 上位50本の候補論文からなる順位列 | §3 |
| **読解**（Reader） | 質問文と候補論文50本 | 提出論文の選択、根拠箇所、最終回答 | §4 |

本番入力には問題型の注釈を含めない。2つのモジュールは**候補論文50本の順位列だけで接続する**。読解モジュールはこの50本を順位で閾値化せず、候補集合として利用する。したがって検索モジュールは、順位付きの出力を維持しながらも、構成の選択では**候補集合の被覆**を重視する（§5.2、§6.1）。この接続の運用が、検索側の目的関数を規定する。

検索モジュールには論文本文を読む LLM を含めるが、**これは読解モジュールとは別のものである**。この LLM の判定は、(a) 反復検索の停止、(b) 次周の再分解の誘導、(c) 論文間展開の起点（anchor）の選択という、3つの内部制御にのみ用いる。すなわち **retrieval controller** として機能する（§3.3）。本稿ではこのモジュールを **Evidence Verifier** と呼ぶ。

Evidence Verifier は、最終的な根拠品質を保証するモジュールではない。候補論文が質問を支持しうるかを判定し、検索処理を制御する内部モジュールである。**最終的な根拠箇所の提示と回答生成は読解モジュール（§4）が担う。**

**本稿の主張は検索モジュールに関するものである。** すなわち、質問起点の検索だけでは届きにくい層が存在し、初期候補からの論文間展開を順位融合することでその層を回収できる、という点にある（§1.4、§6.2）。読解モジュールの設計と評価は §4 で述べる。

## 1.2 Diagnosis: Retrieval Stalls After the First Paper

検証データ55件のうち、複数論文問題は29件である。質問起点の検索のみを行う構成、すなわち本稿のランキング B を除いた構成（§6.2と同一条件）について、各クエリの gold 論文が候補列の何位に現れるかを調べた。各クエリ内では gold 論文を順位の良い順に並べ、集計した（micro、29件）。

| Rank within query | Count | Median rank | @5 | @20 |
| --- | --- | --- | --- | --- |
| 1本目 | 29 | 1位 | 97% | 100% |
| 2本目 | 23 | 7位 | 43% | 61% |
| 3本目 | 22 | 21位 | 32% | 50% |
| 4本目 | 12 | 18位 | 25% | 58% |

1本目の gold 論文はほぼ回収できている。29件中28件では上位5本に入り、83%では1位である。一方、順位が大きく低下するのは2本目以降であり、3本目の中央値は21位である。

したがって、課題は単に平均 recall を向上させることではなく、**1本の関連論文を発見した後に、その周辺を探索すること**だと定式化できる。

## 1.3 Gold Sets Contain Papers the Question Never Names

検証データに含まれる gold 論文について、紐づく `evidence`（根拠箇所の注釈）が1件以上存在するかを集計した。

| Category | Count |
| --- | --- |
| gold 論文の合計 | 146 |
| evidence が紐づく論文（以下、**注釈付き gold**） | 117 |
| evidence が1件も紐づかない論文（以下、**evidence 未注釈 gold**） | 29（19.9%） |

「evidence 未注釈」はデータ上の定義であり、それ以上の意味を付与するものではない。ただし、内容を確認した範囲では、これらの論文は同一トピックに属する周辺論文として機能していた。たとえば、q_036「TCM の batch size は？」の gold には IMM、sCT、Consistency Models Made Easy が含まれ、q_039「IMM の kernel function は？」の gold も同じ4本で構成される。質問文はいずれの論文も名指ししていない。

**この区分は開発時の誤り分析のための道具であり、評価には用いない。** どの gold が回答に直接寄与するかを著者が判定しているわけではなく、区分の基準は `evidence` 注釈の有無という機械的な事実だけである。**採点に用いる指標は gold 全件を分母とし、この区分によって分母を変えることはない**（§5.2）。また本稿の最終的な性能評価はテストデータ（リーダーボード）のスコアで行う（§5.1、§6.9）。

同じ検索条件で2群の回収率を比較すると、両者の回収傾向は明確に異なる（micro、multi 29件）。

| Denominator | @10 | @20 | @50 |
| --- | --- | --- | --- |
| 注釈付き gold（91本） | 0.626 | 0.725 | 0.769 |
| evidence 未注釈 gold（29本） | 0.103 | 0.207 | 0.310 |

本検証条件では、質問起点のランキングは evidence 未注釈 gold に対して大きく性能が低下する。これらの論文を指す語が質問文に含まれないため、質問ベクトルの近傍に現れにくいと考えられる。この問題は検索器の能力だけでなく、質問と gold の対応関係にも由来する。

> 注釈仕様との対応は未確認である。タスク主催者が関連論文も gold に含めると定めているかは、本稿では確認できていない。上記の解釈は著者による観察であり、少数の内容確認に基づく。

## 1.4 Proposal: Rank Fusion with Paper-to-Paper Expansion

§1.2および§1.3の分析は、質問を起点としないランキングの必要性を示している。本稿では、既に発見された論文の近傍論文を検索する「論文→論文」のランキング（**ランキング B**）を構成し、質問由来のランキング（**ランキング A**）と順位融合する（§3.4）。

ランキング B の起点は候補1位の論文に限定しない。Evidence Verifier が質問を支持しうると判定した論文も起点に加えることで、展開可能なトピッククラスタを増やす。

また、チャンク単位で索引しつつ論文単位で評価するというタスク構造に合わせ、融合の単位と論文の代表スコアの算出を論文単位に統一する（§3.2）。

## 1.5 Main Results

**設計は検証データ上で選び、最終的な性能はテストデータのリーダーボードで判断する**（§5.1、§6.9）。以下に示す検証データ上の数値は、設計判断の根拠として得たものである。

検証データ55件における公式指標 `candidate_recall`（macro）は、total で cr@20 = 0.9136、cr@50 = 0.9682、multi_paper で cr@20 = 0.8362、cr@50 = 0.9397 である。診断指標（§5.2）では、total の ecr@20 = 0.9515、multi の ecr@20 = 0.9080 であった。さらに、各クエリについて注釈付き gold をすべて候補50本に含められた割合である All-Gold@50 は、注釈付き gold 基準で **0.9636（53/55）**であった。

本稿の中心提案であるランキング B の寄与を、同一の検索結果から候補列のみを再構成する決定的な対照で測定すると、multi_paper の cr@20 は 0.5862 から 0.8592 に、ecr@20 は 0.7356 から 0.9253 に上昇した（§6.2）。ただし、この対照は Base A+B（§5.3）上での測定であり、最終構成上で同じ対照は未実施である（§7(2)）。

## 1.6 Contributions

1. 検証データの gold の約2割が evidence 注釈を持たないこと、内容を確認した事例では質問文に明示されない周辺論文として振る舞うこと、ならびに複数論文問題では2本目以降の順位が低下することを報告する（§1.2、§1.3）。

1. 初期候補からの論文間展開を順位融合する設計を示し、その寄与を LLM の非決定性を含まない対照実験で測定する（§3.4、§6.2）。

1. 論文単位で評価するタスクに対して、融合の単位と代表スコアを論文単位に統一する設計を示し、その効果と副作用、すなわち浅い順位と深い順位のトレードオフを報告する（§3.2、§6.3）。

# 2. Related Work

本手法は既存要素の組合せに基づく。本節では、既存要素と本稿の差分を明確にする。

**Sparse/dense hybrid retrieval と rank fusion.** 語彙一致に基づく検索 [BM25: Robertson & Zaragoza 2009]、密ベクトル検索 [DPR: Karpukhin et al. 2020]、および Reciprocal Rank Fusion [Cormack et al. 2009] による統合は標準的な構成である。本稿では、チャンク単位ではなく論文単位に畳み込んでから融合する点が異なる（§3.2.2）。評価も論文単位で行うため、融合単位を論文単位に揃えることで指標との整合性を保つ。埋め込みおよび reranker には Qwen3-Embedding と Qwen3-Reranker [Qwen Team 2025] を用いる。

**Pseudo relevance feedback.** 上位文書の語をクエリに追加する手法は、Rocchio [1971] や RM3 [Lavrenko & Croft 2001] 以来広く用いられている。本稿の Seed Expansion（§3.2.3）はその単純な形であり、LLM を使用せず、元の質問を必ず残すことのみを設計上の制約とする。LLM によるクエリ書換え [例：Query2doc, Wang et al. 2023] も実装したが、採用しなかった（§6.7）。

**科学文献検索と論文表現.** 論文単位の埋め込みである SPECTER [Cohan et al. 2020] および SPECTER2 [Singh et al. 2023] は、引用関係を教師として学習される。このため、質問との適合性よりも論文間の近さを捉える表現とみなせる。本稿では、これをランキング B の1ソースとして用いる（§3.4）。

**Citation / bibliographic coupling.** 共有参考文献に基づいて文献間の近さを測る書誌結合 [Kessler 1963] と共引用 [Small 1973] は、いずれも確立した概念である。本稿のコーパスは2024〜2025年の論文に限定されるため、同時期の論文間では直接引用が少ない。そこで、直接引用の代わりに共有参考文献の Jaccard 類似度を用いる（§3.4）。

**Iterative / agentic retrieval.** 検索と生成を交互に行う構成 [Self-Ask: Press et al. 2023; IRCoT: Trivedi et al. 2023] も既存である。本稿では、読解結果を回答生成に用いるのではなく、論文間展開の起点としてランキングへ還流させる点が異なる（§3.3）。

**本稿の位置付け.** hybrid retrieval、RRF、PRF、論文埋め込み、書誌結合、反復検索という各要素自体はいずれも既存である。本稿が主張するのは、これらを「質問起点ランキング」と「初期候補起点ランキング」の2系統に分け、後者を reranker に通さずに順位融合する構成が、質問文が直接言及しない gold を含む本タスクで有効であるという点である。

# 3. Method

## 3.1 Overview

処理は3層から構成される。

### Layer 1: Question-Anchored Ranking A

```
質問 q ──[属性制約の抽出]──┐
        └─[LLM: クエリ分解]→ サブクエリ4本
                              │
   各サブクエリについて：     │
     [BM25 chunk] [BM25 paper] [FAISS: Qwen3-Emb-8B]
              └──── 論文単位 RRF (k=60、1論文1票) ────┘
                              │
              Seed Expansion（1位論文の語彙を加えて再検索し、
              初回と拡張後の順位を1:1で再融合）
                              │
                      属性フィルタによる絞込み
                              │
              [Qwen3-Reranker-8B] pool_k=200
              順位を置換せず、融合前順位と RRF で統合
                              │
                   上位20チャンク → チャンクプール
```

### Layer 2: Evidence Verification and Iteration (up to 3 rounds)

```
チャンクプール → [LLM: Evidence Verifier] → 3つの内部検索制御信号
                   ├ sufficient  … 反復の停止条件
                   ├ missing     … 次周の再分解を誘導
                   └ paper_ids   … 次段の展開に用いる anchor
不足しており、かつ最終周でなければ、[LLM: 再分解] を行って層1へ戻る
```

### Layer 3: Paper-to-Paper Ranking B and Final Fusion

```
チャンクプール → 論文の代表スコア（max 集約、table チャンクは除外）
                → ランキング A（上位50本に切る前の全長）
                              │
anchor = 候補1位 ∪ Verifier が支持と判定した論文
   ├ SPECTER2：anchor ごとの近傍を交互配置 → 100本 ┐
   ├ 書誌結合：同上                              → 100本 ├→ RRF(k=60) → 近傍候補（100本）
   └ 全文 MLT：同上                              → 100本 ┘   ※ reranker には通さない
                              │
                    anchors を先頭に追加（切り直さない）
                      → ランキング B（最大 100 + |anchors| 本）
                              │
        score(p) = 1/(10 + rank_A) + 1/(10 + rank_B)
                              │
                  candidate_papers（上位50本）
```

LLM の呼出し回数は、1クエリ当たり最大6回である（分解1回、検証3回、再分解2回。下記(b)）。

### Procedure (Pseudocode)

図からは読み取れない処理順と件数を、以下の疑似コードで固定する。

```
constraint ← extract_venue_year(question)           # 元の質問から1回だけ抽出する（§3.2.4）
subqueries ← LLM_decompose(question, constraint)    # 4本に分解する

pool    ← {}      # chunk_id → 最高スコアの結果。全周にわたり蓄積する
verdict ← null    # 直近に成功した検証結果のみを保持する（下記(a)）

for step in 0 .. max_steps-1:                       # max_steps = 3
    for q in subqueries:
        runs ← [index.search(q, fetch_k(constraint)) for index in 3索引]
        runs ← [top_k(attribute_filter(r, constraint), per_index_k) for r in runs]
        fused ← paper_rrf(runs, k=60, chunks_per_paper=3, top_k=pool_k)   # §3.2.2
        if seed_expansion:                                                # §3.2.3
            q2    ← q + title_abstract(paper_of(fused[0]))[:512]
            runs2 ← [index.search(q2, fetch_k(constraint)) for index in 3索引]
            runs2 ← [top_k(attribute_filter(r, constraint), per_index_k) for r in runs2]
            fused2 ← paper_rrf(runs2, k=60, chunks_per_paper=3, top_k=pool_k)
            # 第2段：初回と拡張後を2本のランキングとして同じ融合器で統合する
            fused  ← paper_rrf([fused, fused2], k=60, chunks_per_paper=3, top_k=pool_k)
        ranked ← rerank_blend(fused, rerank(q, fused))    # §3.2.5。全候補をスコアする
        pool   ← merge_max(pool, ranked[:20])             # 同一 chunk は高いスコアを残す

    papers ← top_papers(pool, 20)          # 代表スコア順（§3.5）。1論文当たり最大2チャンク
    v ← LLM_verify(question, papers)
    if v ≠ null: verdict ← v               # (a) 失敗した周は前周の判定を保持する
    if verdict ≠ null and verdict.sufficient: break
    if step = max_steps-1: break           # (b) 最終周では再分解を行わない
    subqueries ← LLM_refine(question, verdict.missing if verdict ≠ null else "")

A ← rank_papers(pool)                      # 全長。上位50本に切らない（§3.4(a)）
anchors ← dedup([A[0]] + (verdict.paper_ids if verdict ≠ null else []))  # 順序を固定する

# ランキング B は2段で構成する（§3.4）。各段の処理は異なる。
for s in {SPECTER2, Biblio, MLT}:                        # 第1段：anchor 間の統合
    B_s ← interleave([neighbors_s(a, 100) for a in anchors])[:100]
                                                          # 交互配置と重複除去により、1論文は1回だけ出現する
B ← RRF([B_SPECTER2, B_Biblio, B_MLT], k=60)[:100]        # 第2段：ソース間では加点される
if B = ∅: return top50(A)                                 # 近傍がなければ A のみを返す
B ← anchors + [p for p in B if p ∉ anchors]               # §3.4(b)。切り直さない
                                                          # |B| ≤ 100 + |anchors|
return top50(rrf_AB(A, B, k=10))
```

**(a) 検証結果は累積せず、直近に成功した1件のみを用いる。** ある周で判定が返らなかった場合は、前周の判定を保持する。したがって anchor は、最後に成功した周の `paper_ids` であり、全周の和集合ではない。再分解に渡す `missing` も同じ判定から取得する。一度も判定に成功していない場合は、空文字列を渡す。

**(b) 最終周では再分解を行わない。** 生成しても利用されないためである。これにより、1クエリ当たりの LLM 呼出しは最大6回となり、最終周にも再分解を行う実装より1回少ない。

**(c) ランキング B の2段は非対称である。** 第1段では anchor 間で交互配置し、重複を除去する。そのため、複数の anchor に支持された論文であっても1回だけ数える。第2段ではソース間を RRF で統合するため、複数のソースに現れる論文はソース数に応じて加点される。この非対称性は意図した設計であり、理由は§3.4で述べる。近傍論文が1本も得られない場合はランキング B を構成せず、ランキング A の順位をそのまま返す。

**件数の関係.** `per_index_k = 100` は、各索引が融合処理に渡す件数である。属性フィルタが適用される場合は、絞込みによる減少を見込んで、索引から `fetch_k = clamp(per_index_k / 選択率 × 1.5, per_index_k, 3000)` 件を取得し、フィルタ後に `per_index_k` 件へ切り詰める。上限3,000の根拠はAppendix Cに示す。`pool_k = 200` は融合処理が出力するチャンク数であり、§3.2.2のとおり1論文当たり最大3チャンクとするため、少なくとも67論文に相当する。

**擬似チャンクの扱い.** 論文単位 BM25 が返す `{paper_id}#paper` は、順位付けには寄与するが、論文の代表チャンクとしては最後に選択する。したがって、実チャンクを1本でも持つ論文は必ず実チャンクで代表され、擬似チャンクが後続処理に渡るのは、その論文の実チャンクが候補列に1本も残っていない場合に限られる。この規則は融合処理の内部で完結しており、擬似チャンクを除外して `pool_k` に欠員を生じさせる実装にはしていない。

**Verifier に渡す際の変換規則.** プールを論文単位に畳み込み（§3.5）、代表スコア上位20論文を採用する。各論文について、スコア順に最大2チャンク、各1,800文字までを提示する。チャンクが1本しかない論文については、その1本のみを提示する。実チャンクを1本も持たない論文については繰り下げず、擬似チャンクに対応する本文の先頭1,800文字をそのまま提示する。すなわち、Verifier の入力は常に上位20論文であり、実チャンクの有無によって論文を入れ替えることはない。

ここで「実チャンクを持たない論文」とは、コーパスにチャンクが存在しない論文ではない。候補列に当該論文の実チャンクが残らず、論文単位 BM25 に由来する擬似チャンクだけが残った場合を指す。擬似チャンクに対応する本文は、論文単位索引の索引文書、すなわち `[venue year] title` と当該論文の全チャンク本文を連結したものである。`{paper_id}#paper` という ID 自体は実在しないが、本文は索引内に存在する。

## 3.2 Ranking A (Question-Anchored)

### 3.2.1 Corpus, Chunking, and Indexes

PDF を MinerU で構造化し、最大2,000文字の5種類のチャンクに分割する。コーパスは、2024〜2025年のトップ会議論文27,487本、2,564,545チャンクからなる。

| `chunk_type` | Count | Share |
| --- | --- | --- |
| `text_span` | 1,676,229 | 65.4% |
| `equation_algorithm` | 328,467 | 12.8% |
| `figure` | 319,418 | 12.5% |
| `table` | 212,944 | 8.3% |
| `title_abstract` | 27,487 | 1.1% |

全チャンクの先頭には `[venue year] paper title` を付与する。このため、質問文に会議名が含まれる場合、BM25 はこの表記にも一致する。(venue, year) の組合せは9通りであり、2024年は ECCV のみである。

索引は3種類用いる。粒度の異なる2種類の語彙一致索引と、1種類の意味検索索引である。

| Property | BM25 (chunk) | BM25 (paper) | Dense |
| --- | --- | --- | --- |
| 単位 | チャンク 2,564,545 | 論文 27,487 | チャンク 2,564,545 |
| 実装 | `bm25s`（Lucene、k1=1.5、b=0.75） | 同左 | FAISS `IndexFlatIP` |
| モデル | — | — | Qwen3-Embedding-8B、4,096次元、fp16 |
| サイズ | 5.1 GB | 2.9 GB | 42.0 GB |

論文単位 BM25 を用いるのは、質問語が論文内の離れた箇所に分散する場合、1チャンク内に語が揃わず、チャンク索引が不利になるためである。一方、論文単位の索引では、表の1セルのような局所的な根拠が埋もれる。両者は相補的である（§6.4）。

> 論文単位索引が返す `chunk_id` は `{paper_id}#paper` という擬似 ID であり、実在しない。ID は根拠箇所として参照できないが、対応する索引文書の本文は存在する。順位付けには利用し、代表チャンクには実チャンクを優先して用いる（Appendix B）。

### 3.2.2 Paper-Level RRF

各索引の結果を、**チャンクではなく論文単位に畳み込んでから融合する**。

```
s(p) = Σ_i w_i / (k + paper_rank_i(p))        （k = 60、すべての重みは1.0）
paper_rank_i(p) = 索引 i の結果において、p が最初に現れる位置（0始まりの密順位）
```

1つの索引の結果において、同じ論文に複数チャンクが一致しても、その論文には1票のみを与える。チャンク単位で融合すると、3位、4位、5位にチャンクを持つ論文は `1/61 + 1/62 + 1/63 = 0.0484` を得る一方、1位に1本だけチャンクを持つ論文のスコアは `1/61 = 0.0164` であり、前者は後者を約3倍上回る。この場合、長い論文や表の多い論文が、質問との関連性とは別の理由で上位に現れやすい。

出力は後続の処理が `chunk_id` を利用するため、チャンク列のままとする。ただし、論文の順位を主キー、論文内のチャンク順位を副キーとして並べる。1論文が出力できるチャンクは最大3本とする。制限しなければ、100チャンクを持つ1論文だけで `pool_k` の半分を占める可能性がある。

> チャンク単位の `pool_k = 200` は200チャンクを意味する。一方、論文単位 RRF では1論文当たり最大3チャンクであるため、少なくとも67論文を含む。reranker の推論回数は変わらない。

### 3.2.3 Seed Expansion

```
expanded = 元の質問 + 1位論文の title + abstract の先頭512文字
```

初回検索の順位と拡張後検索の順位を融合してから、reranker に渡す。LLM は使用しない。

Seed Expansion は reranker の前に置く。後段に置くと reranker の推論回数が2倍になるが、前段に置く場合、追加される処理は索引検索1回のみであり、reranker は元の質問に対して1回だけ実行される。

融合は2段階で行う。まず、初回の3索引を融合して1本のランキングを作り、拡張後の3索引についても同様に1本のランキングを作る。次に、この2本を2つの run として、同じ融合器で再度融合する。6本の索引結果を一括で融合しないため、拡張側の3索引だけが初回側より票数で有利になることはない。初回と拡張後の寄与は1:1であり、第2段も§3.2.2の論文単位 RRF であるため、融合単位は一貫して論文単位である。

反復ループ内ではサブクエリごとに Seed Expansion が実行されるため、1クエリ当たり最大12回（4サブクエリ × 最大3周）の拡張が行われる。

### 3.2.4 Query Decomposition and Attribute Filtering

質問を LLM により4本のサブクエリへ分解する。本数は固定し、返り値も4本に切る。問題型に応じた本数の振分けは行わない。本番入力には問題型がなく、分類器を導入して得られた利得も平均0.58本にとどまったためである（Appendix C）。

質問文に会議名が明示される場合のみ、検索結果を当該会議に絞り込む。検索結果のメタデータに venue と year が含まれるため、索引を改修せずに、各索引から多めに候補を取得してからフィルタする。年のみが指定される場合、`all venues` を含む場合、または会議名が2種類以上含まれる場合には、フィルタを適用しない。絞込み後の候補が10件未満であれば、フィルタなしの結果に戻す（fail-open）。検証55件中5件でフィルタが適用され、制約を満たす gold は18/18であった。

### 3.2.5 Rank Fusion with the Reranker

Qwen3-Reranker-8B（fp16、`max_tokens=2048`）に、融合後の上位 `pool_k = 200` チャンクを入力する。指示文は次のとおりである。

> Given a scientific question, retrieve passages from research papers that help identify or support the answer.

reranker の順位で既存順位を置換するのではなく、融合前の順位と再度融合する。

```
score(c) = w_orig / (k + rank_fused) + w_rerank / (k + rank_reranked)
w_orig = 0.6,  w_rerank = 0.4,  k = 60,  protect_top = 20
```

質問適合性を主に最適化する reranker は、質問文が直接言及しない論文（§1.3の群）を下位へ移す可能性がある。このリスクを避けるため、ランキング B は reranker に通さない。一方、ランキング A の内部では融合前の順位が失われてしまうため、`protect_top` により融合前の上位20件の集合を先頭に残し、21位以下の候補が無条件に上位へ入ることを防ぐ。

ここではスコアではなく順位のみを用いる。RRF スコアと yes 確率はスケールが異なるためである。推論コストは増えない。実装はもともと全候補をスコアしてから切り詰めている。

## 3.3 Evidence Verification and Iteration

LLM（GPT-5.4、`reasoning_effort=medium`）に、上位20論文について各論文最大2チャンク、各1,800文字を読ませ、4つの field を返させる。いずれも最終的な出力物ではない。

検索制御に用いる返り値は、`sufficient`、`missing`、`paper_ids` の3つである。

| Return value | Role | Output? |
| --- | --- | --- |
| `sufficient` | 反復を停止する | いいえ |
| `missing` | 次周の再分解を誘導する | いいえ |
| `paper_ids` | 質問を支持しうると判定された論文。ランキング B の anchor とする（§3.4(d)）。 | いいえ |
| `evidence_chunk_ids` | 下流チームとの共有ログ | いいえ |

`evidence_chunk_ids` は検索経路にも評価にも関与しない。実装がこの値を予測ファイルに書き出すのは、共有ログとして残すためである。検索側の観点では、この項目を構造化出力から除くことで、返答形式の失敗率を下げられる余地がある（§6.6では取得率が課題として残る）。

停止条件には `sufficient` のみを用いる。以前は規定本数の論文が見つかった時点で停止していたが、検索は毎回20件を返すため、初回で条件を満たしてしまい、反復が1周も実行されなかった。

この判定は、もう1段の reranker としても機能する。ただし、支持と判定された論文の gold 率は68本中52本（76%）であり、候補1位の85%（47/55）より低い。それでも順位に寄与するのは、判定精度そのものではなく、展開の起点数を増やすためである（§3.4(d)）。

## 3.4 Ranking B and A/B Fusion

anchor の近傍論文を3種類の近さに基づいて取得し、2段階で融合する。各段の出力は上位100本であり、ソース間の RRF 定数は `k=60` とする。ランキング B の構成では GPU も LLM も用いない。

| Source | Definition of proximity |
| --- | --- |
| SPECTER2 | 論文近接性埋め込みにおける近傍（title + abstract） |
| 書誌結合 | 参考文献の arXiv ID 集合に対する Jaccard 類似度（共有2本以上） |
| 全文 MLT | 論文単位 BM25 に対する more-like-this 検索 |

### Two-Stage Fusion

```
第1段（anchor 間、ソース内）：B_s = interleave([N_s(a) | a ∈ anchors])[:100]
第2段（ソース間）：           B   = RRF({B_s | s ∈ {SPECTER2, 書誌結合, 全文MLT}}, k=60)[:100]
```

`N_s(a)` は、anchor `a` に対するソース `s` の近傍100本である。

第1段は RRF ではなく、交互配置（`interleave`）である。anchor ごとの近傍リストを順位方向に交互に並べ、同じ論文が既に現れていれば除外する。したがって、同じ論文が複数の anchor の近傍に現れても、`B_s` には1回しか入らない。複数の anchor に支持されたこと自体は加点にならず、いずれかの anchor の近傍で上位に現れたことのみが反映される。これは、1つの anchor の遠い近傍よりも、別の anchor の近い近傍を優先するための設計である。

第2段は RRF であるため、複数のソースに現れた論文はソース数に応じて加点される。§1.3の論文群を回収する経路は3種類あり、複数の経路に現れる論文を上位に配置したいためである。

この非対称性は意図した設計である。anchor は同じ質問に対する複数の入口であり、anchor 間の合意を数える意義は小さい。一方、ソースは異なる種類の近さを表すため、ソース間の合意は有用な信号となる。anchor ごとの合意も数える変種、すなわち各 anchor × 各ソースを別々の項として RRF に入力する変種も実装したが、@20と@50が悪化したため、既定では用いない（Appendix C）。

anchor 列の順序は第1段の交互配置に影響するため、固定する。先頭は必ずランキング A の1位とし、その後に Verifier が返した `paper_ids` を返答順のまま追加する。重複する論文については、先に現れたものを残す。すなわち、`anchors = dedup([A[0]] + verdict.paper_ids)` とする。

第2段で上位100本に切った後に anchor を先頭へ加えるため、最終的な B の長さは最大で `100 + |anchors|` 本となる。anchor が B に含まれていなかった分だけ長くなる。末尾を再度切り詰めないのは、B 単独で回収できていた論文が消えることを避けるためである。§3.4冒頭の「各段とも上位100本」は第1段および第2段の出力を指し、anchor を追加した後の最終 B には当てはまらない。

B が空の場合は、A の順位をそのまま返す。

書誌結合は引用グラフではない。本コーパスは2024〜2025年に限定され、anchor から解決できたコーパス内引用は実測で1本だった。一方、共有する古い文献の Jaccard 類似度は、TCM とその周辺3論文の間で0.19〜0.24であり、無作為に選んだ30論文では中央値0.000、最大0.054であった。共有参考文献が1本だけの場合を除外するのは、汎用的に引用される文献を介した接続を避けるためである。

ランキング B は reranker に通さない（§3.2.5と同じ理由）。

ランキング A と B は、次式により順位融合する。

```
score(p) = w_A / (k + rank_A(p)) + w_B / (k + rank_B(p))
k = 10,  w_A = w_B = 1.0
```

設計上の要点は次の4点である。数値的な根拠は§6.3およびAppendix Cに示す。

**(a) A は上位50本に切る前の全長を用いる。** A を先に切り詰めると、51位以下の論文を B が上位へ押し上げられない。

**(b) anchor 自身を B の先頭に置く。** 各ソースは anchor を自らの近傍候補から除外する。そのままでは anchor は A の1項しか持たず、A と B の両方に存在する論文（2項）に順位で抜かれる。実測では、anchor を先頭に追加しないと single_paper の cr@20 が1.000から0.923に低下した。この先頭追加は B が非空の場合にのみ行う。近傍候補が1件も得られない場合は B を構成せず、A をそのまま返すため、追加先が存在しない。

**(c) 融合定数は `k=10` とする。** B に含まれない A の1位は `1/(k+1)` を得る。一方、A と B の双方で `r` 位（0始まり）の論文は `2/(k+1+r)` を得るため、後者が前者を上回る条件は `r < k+1` である。`k=60` では、リスト長50本に対して閾値が `r<61` となり、両方に載っていれば深い順位の論文でも A の1位を上回ってしまう。`k=10` では、両方のランキングで上位に位置する論文のみが A の1位を上回る。

**(d) 起点は「候補1位 ∪ Verifier が支持と判定した論文」とする。** 候補1位は必ず残す。Verifier が判定した論文のみを起点とすると、(b) と同様の問題が生じ、single_paper の cr@1 が0.923から0.885に低下した。

## 3.5 Chunk-to-Paper Aggregation and Output

反復終了後、チャンクプールを論文のランキングに畳み込む。論文の代表スコアは、**table チャンクを除いた最大スコア**とする。

```
s(p) = max({s(c) | c ∈ p, chunk_type(c) ≠ table} ∪ {0})
```

`table` チャンクは数値と短いラベルが密集しているため、語の重なりだけで高いスコアが付きやすい。このため、質問の主題ではない論文でも代表スコアが高くなりうる。ただし、チャンクプール自体は変更しない。`table` チャンクは Verifier にそのまま渡す。

`table` チャンクは、検証の材料であって昇格の根拠ではない。候補論文は代表スコア順に上位20本を Verifier に渡すため、`table` チャンクしか候補に残っていない論文の代表スコアは0となり、通常は Verifier に到達しない。`table` チャンクが機能するのは、非表チャンクにより上位に入った論文に対する検証材料としてである。`table` チャンクだけでランキング A の上位へ論文を押し上げることはない。表を提示した場合には Verifier が gold を確認できた割合が71%であり、提示しない場合の51%を上回った。このため、順位付けでは雑音となりうる一方、検証には有用な材料である。

検索モジュールの出力は候補論文50本からなる順位列のみである。提出論文の選択、回答生成、根拠箇所の提示は行わず、これらは読解モジュール（§4）が担う。読解モジュールはこの50本を順位で閾値化せず、候補集合として利用する。

**入力方法.** 検証データにのみ存在するフィールド、たとえば問題型は削除してから入力する。これらを与えたまま評価すると、本番時の入力条件と乖離するためである。

| `candidate_recall@k`（cr@k） | gold 論文の全件 | クエリごとに計算し macro 平均 | 採点仕様に沿った主評価 | 主表の左側 |
| `evidence_candidate_recall@k`（ecr@k） | 注釈付き gold のみ（§1.3） | 同上。分母が空のクエリは集計から除外 | 設計の効果を分析する診断指標 | 主表の補助列 |
| All-Gold@k | クエリ | 対象 gold をすべて候補に含めた割合 | 必要な論文をすべて揃える難しさの評価 | 補助表（基準を明記） |

**指標には3つの階層がある。** 最終的な性能はリーダーボードのスコアで判断する（§6.9）。検証データ上では cr@k を主評価とし、ecr@k は設計を分析するための診断指標にとどめる。

ecr@k は§1.3の群を分母から除くため、cr@k より高い値になりやすい。**この指標で最終性能を主張することはしない。** また gold のどれが回答に直接寄与するかを著者が判定しているわけではなく、分母の差は `evidence` 注釈の有無という機械的な事実だけに基づく。採点仕様に対応する cr@k と `paper_recall` の分母は常に gold 全件であり、注釈付き gold を完全に回収できた場合でも、本検証集合上の `paper_recall` の上限は multi で0.836、全体で0.914となる。

§1.2および§1.3の分析は gold 論文数に基づく micro 集計であり、主評価とは集約単位が異なる。以降の表では、集約単位を明記する。

**上の3指標は検索モジュールの評価指標である。** 根拠箇所の提示と回答の正しさは読解モジュールの成果物であり、その指標（evidence precision / recall / F1、および回答の正誤）は §4 で定義して報告する。**検索モジュールの構成選択は上の3指標だけで行い、読解側の指標は用いない**——読解側の値は読解モジュールの実装にも依存するため、検索の設計判断の根拠にすると交絡するためである。

なお、検索モジュール内部の Evidence Verifier が返す `evidence_chunk_ids` は、**読解モジュールが出力する根拠箇所とは別物**である。前者は検索を制御するための内部返り値であって、評価対象としない。本稿が Verifier について報告するのは、判定が取得できたかどうか（§6.6）のみである。これは出力品質ではなく、ランキング B の起点が何件のクエリで成立したかを表す検索側の量である。本システムでは、この取得率が Base A+B より低下している（46/55から40/55）。この点は、最終構成を選択する際の判断材料として考慮する必要がある（§6.1）。

## 5.5 Reproducibility

LLM は非決定的であり、クエリ数も55件に限られるため、数ポイントの差を実行間のばらつきと区別できない。本稿では、比較を次の2種類に明確に分ける。

- **決定的な比較**：同一の検索結果から候補列の組立てのみを再実行する。LLM のばらつきを含まない（§6.2、§6.3の設定比較）。候補列を組み直した結果が通常実行の結果と55件すべてで一致することを確認している。

- **LLM を含む比較**：構成ごとに1回ずつ実行した値である（§6.1、§6.3の主比較、§6.5）。複数回実行した場合の平均および標準偏差は取得していない。1構成当たり数時間を要するためである。

Verifier の返答順も実行間で変化しうる。したがって、anchor 列の順序、さらに第1段の交互配置を経た最終順位も、LLM を含む比較では非決定的である（§3.4）。

### Why This Configuration Is Selected

主表は、本システムがすべての指標で優れることを示していない。@20では Base A+B が優れ、single_paper の cr@1もBase A+Bのほうが高い。それでも本システムを最終構成とする根拠は、次の2点にある。いずれも成立条件を明示できる。

**(1) 読解モジュールは候補50本を順位で切らず、候補集合として利用する。** これは検索側の仮定ではなく、候補列を受け取る読解モジュールの担当者に確認した運用である。§1.1のとおり、提出論文の選択は読解モジュールが担うため、本システムが最適化すべき対象は順位そのものではなく、50本の候補集合の被覆である。この観点に対応する指標は cr@50 と All-Gold@50 であり、いずれも本システムが上回る（total の cr@50は0.9591から0.9682、gold 全件基準のAll-Gold@50は0.8727から0.8909）。

この運用が、検索側の指標選択を規定する。仮に読解モジュールが上位20本のみを利用するなら、@20で優れる Base A+B を選択すべきであり、以下の議論は成り立たない。読解側の cutoff が変われば、最終構成の選択も変わる。

**(2) @20における低下は、読解モジュールが利用しない順位帯での並べ替えである。** 上位20本という切り口は読解側の運用に対応しないため、@20の差は候補50本内での並べ替えにとどまる。multi の cr@20における−0.023は、29件・gold 論文数で見れば数本の差に相当する（§7(1)）。一方、cr@50の+0.009およびAll-Gold@50の+0.018は、あるクエリについて gold 論文をすべて揃えられたケースが1件増えたことに対応する。どちらもノイズと区別できる規模ではない。したがって、この選択は読解側の運用に対応する指標で劣っていないことの確認であり、有意差を主張するものではない。

## 6.6 Queries Where the Evidence Verifier Returns No Judgment

Verifier の判定はランキング B の起点に用いるため（§3.4(d)）、判定取得率は最終順位に影響する。

| Configuration | Queries with at least one judgment |
| --- | --- |
| 本システム | 40 / 55（73%） |
| Base A+B | 46 / 55（84%） |

各周では常に20件の候補を Verifier に渡しているため、候補が空だったことが失敗の原因ではない。起点拡張が実際に機能するのは約4分の3のクエリに限られ、残りのクエリでは候補1位の論文のみを起点とする。本システムで取得率が低下した理由は、本実験では切り分けられていない。

**失敗時の挙動.** 判定が利用できない場合、再試行は行わず、`sufficient` を偽として次の反復へ進む。起点は候補1位の論文のみに戻るため（§3.4(d)）、当該クエリにおける論文間展開は1つのクラスタに制限される。この失敗は§6.1で本システムを最終構成とする判断に対する負の材料であり、Base A+B のほうが取得率は高い。

## 6.7 Error Analysis: Vocabulary Mismatch between Question and Corpus

Seed Expansion（§3.2.3）が対象とする失敗モードの代表例を示す。

q_022「reference-free な preference optimization を提案した ICML 2025 論文の列挙」では、gold 論文の1つである AlphaPO は候補列の28位に位置した。本文中で `reference-free` に該当する表現は参考文献の1件に現れるのみであり、AlphaPO 自身はこの語で自らを記述していない。論文内の表現は `Direct Alignment Algorithm` および `reward shape` であり、いずれも質問文には含まれない。これらの語で検索し直すと、BM25 単体でも1位に回収できる。

これは1例に基づく観察であり、同種の事例を網羅的には集計していない。LLM にクエリを書き換えさせる構成も実装したが、候補列に既に含まれる論文のタイトル語を80%以上含むサブクエリの割合が1%から16%へ増加し、既に得られている論文を再検索する傾向が強かった（multi cr@20 = 0.8161）。この失敗を避けるため、Seed Expansion では元の質問を必ず残し、機械的に連結する方式を採用した。

スコアは提出結果が確定した時点で記載する。テストデータのアノテーションは検証データより粒度が揃っているため、**検証データ上で選んだ設計がテストデータでも有効かどうかは、この表によってのみ確認できる。**

# 7. Limitations

**(1) 検証データは55件であり、開発用と最終評価用に分割していない。** §5.1のとおり、同じ55件を誤り分析、設計選択、パラメータ選定に用いた。したがって検証データ上の数値には過適合の可能性があり、本稿はこれを最終性能の主張には用いず、リーダーボードのスコア（§6.9）で判断する。また、LLM は非決定的であるため、数ポイントの差を実行間のばらつきと区別できない。複数回実行した場合の平均および標準偏差は取得していない。

**(2) 中心主張に対応する対照を、最終構成上では測定していない。** §6.2のAのみ対A+Bは Base A+B 上での測定であり、最終構成でも同じ利得が得られるかは確認できていない。§6.4〜§6.6も同様に Base A+B 上で測定している。また、3つの改良は同時に導入しており、@20の低下がどの要素に由来するかを分離できていない。

**(3) 外部・標準ベースラインとの比較がない。** 本稿の結果は内部構成間の比較に閉じている。主催者が公開するベースライン、密ベクトル単体、BM25と密ベクトルの RRF（reranker なし）、reranker の単独寄与は測定していない。測定済みなのは、BM25の索引粒度（§6.4。ただし縮約条件）と、ランキング A / A+B（§6.1、§6.2）のみである。既存の標準的な検索構成に対する位置付けは示せていない。

**(4) テストデータの gold は手元にない。** 我々が確認できるのは §6.8 の出力健全性までであり、性能はリーダーボードのスコアを通じてのみ観測できる（§6.9）。そのため、テストデータ上での誤り分析や、どの設計要素がテストデータで効いたかの分離はできない。問題型の分布も検証データと大きく異なる。

**(5) gold に関する解釈は著者の観察に依拠する。** §1.3の evidence 未注釈 gold はデータ上の定義であるが、これらが周辺論文として機能するという解釈は少数の内容確認に基づくものであり、注釈仕様との対応は確認できていない。**この区分は開発時の分析にのみ用い、採点指標の分母を変えることには用いていない。** テストデータのアノテーションは検証データより粒度が揃っているため、検証データ上の観察がテストデータにも当てはまるかは、§6.9のスコアによってのみ確認できる。

**(6) Evidence Verifier の判定が約4分の1のクエリで得られない。** §6.6で示したとおり、その場合、ランキング B の起点は候補1位の論文のみに戻る。これは出力フォーマットの失敗に起因し、フォールバックは起点を増やさないことだけである。

**(7) 質問文のみを用いる本検証条件では、直接回収が難しい論文群が残る。** §1.3の群を分母に含む `paper_recall` は、注釈付き gold のみを完全に回収した場合、本検証集合上で計算される上限が multi で0.836、全体で0.914となる。これはデータの注釈状況に対して計算される値であり、タスクの原理的な限界を示すものではない。

---

# 8. Conclusion

科学論文 QA の候補論文検索では、質問起点のランキングだけでは到達しにくい論文群が存在することを、**開発用の検証データに対する誤り分析**により示した。複数論文問題では、1本目を回収できても2本目以降の順位が低下する。また gold の約2割は evidence 注釈を持たず、内容を確認した事例では質問文に明示されない周辺論文であった。

これに対して、初期候補および検証済み論文を起点とする論文間展開のランキングを構成し、質問起点ランキングと順位融合する設計を示した。LLM の非決定性を含まない対照実験では、この設計により multi_paper の cr@20 が0.5862から0.8592へ、ecr@20が0.7356から0.9253へ上昇した。ただし、これは Base A+B 上での測定であり、最終構成上での同じ対照は今後の課題である。

さらに、チャンク単位で索引しつつ論文単位で評価するタスク構造に対して、融合の単位と代表スコアを論文単位に統一する設計を示した。この変更には、候補50本の被覆、すなわち cr@50およびAll-Gold@50を改善する一方、上位20本の精度を低下させるトレードオフがある。本稿が前者を最終構成として採用するのは、候補列を受け取る読解モジュール（§4）が上位50本を順位で切らずに利用するためである（§6.1）。読解側の cutoff が変われば、最終構成の選択も変わる。各要素がどの指標に寄与したかを分離することは、今後の課題である。

**設計は検証データ上で選び、性能はテストデータのリーダーボードで判断する。** 検証データにはアノテーションの粒度に幅があり規模も小さいため、そこでの数値は設計判断の根拠として用い、最終的な性能の主張には用いない（§5.1、§6.9）。

**以上は検索モジュールに関する結論である。** 読解モジュールの設計と評価は §4 で述べる。

# Appendix B. Implementation Notes

**論文内順位をスコアに書き戻す。** 下流の各段、すなわちチャンクプールへの蓄積、候補論文の並替え、論文単位への集約は、すべて `score` に基づいて並べ直される。返り値の並び順だけに順位を持たせると、後続処理で失われる。このため、論文内の順位を微小なオフセットとしてスコアへ反映する。

```
chunk_score = s(p) − offset × 1e-9    （offset は論文内の順位）
```

`1e-9` が論文間の順位を壊さないことは計算により確認できる。論文間スコア差の下限は `1/(k+r) − 1/(k+r+1) ≈ 1/(k+r)^2` であり、`k=60`、`r=200` の場合でも `1.5e-5` である。1論文当たり最大3チャンクであれば、オフセットは最大でも `2e-9` にとどまる。

**擬似チャンクは代表チャンクに選ばない。ただし、ID と本文を区別する。** `{paper_id}#paper` は実在する `chunk_id` ではないため、根拠箇所として提出・参照することはできない。一方、この ID に対応する論文単位索引文書の本文、すなわち `[venue year] title` と全チャンク本文を連結した文書は実在し、候補列に実チャンクが残らない論文に対する Verifier 入力として用いる（§3.1）。代表チャンクの選択では実チャンクを優先し、擬似チャンクは最後に選択する。これは、順位付けに寄与している論文が候補から消えることを防ぐためである。

**`protect_top` もスコアに反映する。** 並び順だけで候補を先頭へ寄せても、後続処理で並べ直された時点で元に戻る。最大スコアに1を加えることで、集合内の融合順位を保ったまま先頭に配置できる。

**サブクエリ生成プロンプトの注意.** 検索先がローカル索引であることを明示しないと、再分解で生成されるサブクエリの29〜41%にWeb検索演算子（`site:` / `filetype:`）が含まれ、2周目以降の検索が空振りする。属性制約を抽出できた場合は、サブクエリの先頭に `[NAACL 2025]` の形式で付与する。チャンク本文がこの表記で始まるため、検索語として有効に機能する。

# Appendix C. Provenance of Design Choices

**サブクエリ数を4本に固定した根拠.** 問題型に応じて本数を振り分ける設計では、分岐のためだけに分類器が LLM を1回呼び出していた。この変更による利得は平均0.58本にとどまり、分類精度も LLM が0.67、ヒューリスティックが0.673であり、差はなかった。返り値も4本に切る。再分解では平均8.2〜9.3本、最大20本までサブクエリが増加していたが、全812本を1本ずつ除外して候補列を再構成すると、ecr@50の gold が減るのは812本中5本のみであった。

**属性フィルタの取得件数を3,000に抑える根拠.** 絞込み後に `per_index_k` 件を残すよう選択率から逆算すると、NAACL（選択率4.3%）では34,560件の取得が必要になる。`IndexFlatIP` は全走査であるため、取得件数がそのまま計算量に影響する一方、取得した候補の多くはフィルタ後に切り詰められる。件数が足りない場合は fail-open でフィルタなしの結果に戻す。

**A/B 融合のパラメータ.** `related_offset`、`related_weight`、B内部のRRF定数、ソース別重み、ソース別近傍数、2ホップ展開、A∩Bへの明示的なボーナスを、4つの検索構成の出力上で探索した。これらはいずれも現行設定を上回らなかった。起点数を3本に増やす設定も、4構成のうち3構成で悪化した。

**採用しなかった機構.**

| Mechanism | Decision |
| --- | --- |
| 近傍論文を候補列の末尾へ固定数だけ追加する | 採用しない。順位融合と役割が重なり、末尾追加では上位順位を改善できない。 |
| 一意な手法名により候補圏外の論文を救済する | 効果がなかったため削除した。質問文が名指しした28本はすべて既に候補1〜4位にあった。 |
| 表・図の種別による絞込み | 保留。本番データでは適用されない見込みである。 |
| 属性へのソフトな加点 | 採用しない。hard filter と fail-open で同じ目的を達成できる。 |
| 位置挿入による展開 | 順位融合に対して全指標で劣った（cr@20：0.822対0.879）。 |
