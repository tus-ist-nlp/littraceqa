# 検索システム — 論文原稿の素材

論文の章立て（Introduction / Method / Experimental Results）に沿って並べてある。

> Reader（論文の読解 → 回答生成）は読解チームの担当なので、この文書では扱わない。
> 本システムが渡すのは**候補論文の順位列**と**根拠チャンク（evidence）**までである。

## 0. この文書の書き方

設計上の判断はすべて、次の4段で書いてある。**数値だけを唐突に出さない。**

| 段 | 内容 |
|---|---|
| **設定** | 何を、どのデータで、どう測ったか |
| **結果** | 得られた数値 |
| **解釈** | その数値が何を意味するか |
| **設計** | だからシステムをどう作ったか |

数値はすべて検証データ55件での実測値である。

# 1. Introduction

## 1.1 タスクと成果物

質問に答えるための根拠を持つ論文を、27,487本のコーパスから同定する。
出力は**候補論文の順位列（上位50本）**と、そのうち読解で根拠が確認できたチャンクである。
**提出論文の選定と回答生成は行わない。**

以降 §1.2〜§1.5 では、システムを設計する前に検証データを観察して分かったことを述べる。
Method（§2）はこの観察に対する答えとして構成されている。

## 1.2 検証データの gold には2種類ある

### 設定

検証データ55件の gold 論文について、その論文に紐づく `evidence`（根拠箇所の注釈）が
1件でも存在するかを数えた。

### 結果

| | 本数 |
|---|---|
| gold 論文（合計） | 146 |
| **evidence が紐づいている**（以下「根拠付き gold」） | **117** |
| evidence が1件も紐づいていない（以下「ピア gold」） | **29**（19.9%） |

ピア gold の中身を読むと、**質問文が名指ししていない同トピックの論文**であった。
例として、q_036「TCM の batch size は？」の gold には IMM / sCT /
Consistency Models Made Easy が並び、q_039「IMM の kernel function は？」の gold は
**まったく同じ4本**である。

### 解釈

質問文が求めているのは「TCM の batch size」なので、**その質問文をどうベクトル化しても、
近傍にピア論文は来ない**。これは検索器の性能不足ではなく、**質問と gold の関係が
「質問に答える論文」だけではない**というデータの構造による。

### 設計

**評価指標を2本立てにする。** 採点仕様どおり gold 全件を分母にした
`candidate_recall@k`（cr@k）に加えて、**分母を根拠付き gold だけに絞った
`evidence_candidate_recall@k`（ecr@k）**を並べて出す。gold 全件で測ると、
原理的に取れない29本が常に混ざって天井が張り付き、打ち手の改善が薄まって見えるためである。

**打ち手の効きを読むときは ecr を見る。** ただし `paper_recall` の分母は採点仕様どおり
gold 全件なので、根拠付きを完璧に拾っても **multi で 0.836、全体で 0.914 が上限**である。
ecr は打ち手を選ぶための診断指標であって、提出スコアの予測値ではない。

## 1.3 「質問→論文」の1本のランキングでは届かない層がある

§1.2 のピア gold について、実際にどれだけ取れていないかを測る。

### 設定

**質問だけを起点にした検索**がピア gold をどれだけ拾えるかを測る。
具体的には、**ランキング B（論文→論文）を外した候補列**を作り
（§3.3 と同じ条件）、その上位 k 本に対して gold を「根拠付き」と「ピア」に分けて
回収率を測った（micro、multi_paper 29件）。

### 結果

| 分母 | @10 | @20 | @50 |
|---|---|---|---|
| 根拠付き gold（91本） | 0.626 | 0.725 | 0.769 |
| **ピア gold（29本）** | **0.103** | **0.207** | **0.310** |

### 解釈

**同じ検索器・同じクエリでありながら、2群の当たり方は3〜6倍違う。**
これは検索器の精度の問題ではない——**質問文がそもそもピア論文を指していない**ので、
埋め込みモデルを大きくしても reranker を強くしてもこの差は縮まらない。

### 設計

**質問を起点にしない第2のランキングを作る。** 具体的には、
**すでに見つかった論文に近い論文**を引く「論文→論文」のランキング（ランキング B）を
別に構成し、質問由来のランキング（ランキング A）と**順位融合**する（§2.2.6、§2.2.7）。
これが本システムの中心的な設計であり、その寄与は §3.3 で測る。

## 1.4 multi_paper では「2本目以降」が沈む

### 設定

§1.3 と同じ「ランキング B を外した候補列」を使い、multi_paper の29件を取り出す。
各クエリについて、**根拠付き gold（計91本）が候補列の何位に入ったか**を調べ、
**そのクエリの中で順位が良い順に「1本目」「2本目」…と番号を振る**。
番号ごとに、順位の中央値と、上位 k 本に入っていた割合を集計した。

### 結果

| クエリ内の順番 | 本数 | 中央順位 | @1 | @5 | @10 | @20 |
|---|---|---|---|---|---|---|
| **1本目** | 29 | **1位** | 83% | **97%** | 100% | 100% |
| 2本目 | 23 | **7位** | 0% | 43% | 52% | 61% |
| **3本目** | 22 | **21位** | 0% | **32%** | 36% | 50% |
| 4本目 | 12 | 18位 | 0% | 25% | 42% | 58% |

（5本目以降は合計5本しかないので集計から外した。）

### 解釈

**1本目はほぼ完全に解けている**——29件中28件で上位5本に入っており、83%は1位である。
**沈んでいるのは2本目以降**で、3本目の中央順位は21位、上位5本に入るのは3割ほどしかない。

つまり multi_paper の recall が低いのは「gold を見つけられない」からではなく、
**「1本見つけた後が続かない」**からである。したがって問題は
「平均 recall を上げる」ではなく **「1本見つけた後にその周辺を掘る」**と定式化できる。

### 設計

この定式化は §1.3 の結論と同じ設計を指す。**1本目（候補1位）を起点として
論文→論文で近傍を引く**ランキング B が、まさに「周辺を掘る」操作にあたる。
さらに、起点を1本に限らず**読解 LLM が根拠を確認した論文にも広げる**ことで、
展開できるトピッククラスタを増やす（§2.2.7(d)）。

参考までに、ランキング B を入れると同じ集計が次のようになる
（中央順位が 1位 / 3位 / 6位 / 8位、@5 が 100% / 74% / 36% / 33%）。
**2本目の中央順位が7位から3位、3本目が21位から6位に上がる**——
この改善そのものを対照実験として測ったのが §3.3 である。

## 1.5 チャンク単位の検索と論文単位の評価はずれる

### 設定

本文は最大2,000文字のチャンクに割って索引する一方、評価は論文単位である。
そこで**論文の代表スコアを「その論文のチャンクの最大値」で決める**規則について、
**表チャンクを代表に使わない**場合と使う場合を比較した。
比較は候補列を組み直して行い、重み `w` を掛けた形
`max(表以外のチャンク, w × 表チャンク)` の `w` を振った。

### 結果

- `w = 0.85` 以下は**すべて完全に同値**であった（0.8 / 0.5 / 0.1 / 0.0 が小数1桁まで一致）
- 表チャンクを代表から外すと、multi の cr@20 が **+0.020**
- `figure` / `equation_algorithm` を一緒に外すと**悪化**した
- 集約を `max` から `sum` に変えると効果はほぼ消えた

### 解釈

**閾値ではなく「表を代表にしない」という規則そのものが効いている**（`w` に感度が無い）。
効くのが `table` だけで、`sum` 集約では消えることから、これは
**max 集約に固有の歪み**だと分かる。表チャンクは数値と短いラベルが密なので、
BM25 も reranker も語の重なりだけで高いスコアを出しやすく、
**論文が質問の主題でなくても表1枚で代表スコアが跳ね上がる。**

### 設計

論文の代表スコアから表チャンクを外す（§2.2.5）。
**自由パラメータを持たない規則**として書ける点が利点である。
ただし**チャンクプールは変えない**——表チャンクは読解 LLM にそのまま渡し、
evidence にも出せるようにする（理由は §2.2.5）。

## 1.6 設計方針のまとめ

| 課題 | 設計 |
|---|---|
| 質問が名指ししない gold が2割ある（§1.3） | 論文→論文の第2ランキングを作り順位融合する |
| 1本目は解けており2本目以降が沈む（§1.4） | 見つかった論文を起点に周辺を掘る |
| max 集約が表チャンクで壊れる（§1.5） | 論文の代表スコアから表を外す |

# 2. Method

## 2.1 全体像

```
                         質問 q
                           |
        +------------------+------------------+
        |                                     |
 [属性制約の抽出]                      [GPT-5.4: クエリ分解]
 会議名・年を正規表現で                  サブクエリ 4本（固定）
 元の質問から1回だけ取る                  ※LLM 呼び出し 1回
        |                                     |
        +------------------+------------------+
                           v
 +=============== 反復ループ（最大3周）===============================+
 |                                                                    |
 |  各サブクエリ q_i について:                                          |
 |                                                                    |
 |     [BM25]              [FAISS: Qwen3-Embedding-8B]                |
 |     2,564,545 chunks     2,564,545 x 4096 dim                      |
 |          \                      /                                  |
 |           +--> RRF (k=60) --> 属性フィルタで絞込                     |
 |                     |                                              |
 |                     v                                              |
 |         [Qwen3-Reranker-8B]  pool_k = 200                          |
 |          yes 確率で並べ替え                                          |
 |                     |                                              |
 |              上位20チャンク --> チャンクプールへ蓄積                   |
 |                                        |                           |
 |                                        v                           |
 |                        [GPT-5.4: 読解・根拠判定]                     |
 |                        上位20論文 x 2チャンクを読む                   |
 |                        -> sufficient / evidence / paper_ids        |
 |                           ※LLM 呼び出し 1回                         |
 |                                        |                           |
 |         足りなければ [GPT-5.4: 再分解] して次の周へ                    |
 |         十分なら打ち切り（停止条件は sufficient のみ）                 |
 +====================================================================+
                           |
                           v
   チャンクプール --> 論文の代表スコア（max 集約・**表チャンクは使わない**）
                           |
                           v     ランキング A（質問→論文。50本で切る前の全長）
 +==================================================================+
 |  A/B の順位融合                                                    |
 |      score(p) = 1/(10 + rank_A(p)) + 1/(10 + rank_B(p))           |
 |                                                                    |
 |  ランキング B（論文→論文）  ※ reranker に通さない                    |
 |    起点 = 候補1位 ∪ 読解 LLM が根拠を確認した論文                     |
 |     +-- SPECTER2(title+abstract) 近傍 100本                        |
 |     +-- 書誌結合（参考文献の arXiv ID の Jaccard）近傍 100本          |
 |     +-- 全文 MLT（論文単位 BM25 への more-like-this）近傍 100本       |
 |          -> 3ソースを RRF(k=60) で融合                              |
 +==================================================================+
                           |
                           v
        candidate_papers（上位50）  +  evidence（読解が指名したチャンク）
```

**LLM 呼び出しは1クエリあたり最大6回**（分解1 + 読解1 が1周、最大3周）。

## 2.2 Retriever

### 2.2.1 コーパスとチャンク化

PDF を MinerU で構造化し、5種類のチャンク（最大2,000文字）に割る。

| chunk_type | 件数 | 比率 |
|---|---|---|
| `text_span` | 1,676,229 | 65.4% |
| `equation_algorithm` | 328,467 | 12.8% |
| `figure` | 319,418 | 12.5% |
| `table` | 212,944 | 8.3% |
| `title_abstract` | 27,487 | 1.1% |
| **合計** | **2,564,545** | |

**全チャンクの先頭に `[venue year] paper title` を置く。** 質問が「NAACL 2025 の…」と
書いていれば BM25 がこの表記に当たるので、**会議名が検索語として効く**。
本文は「同じ節・同じページ」の間だけ段落を溜めてから切り、節をまたいで結合しない。

コーパスは2024〜2025年のトップ会議 **27,487本**である。

| venue | year | 本数 |
|---|---|---|
| NeurIPS | 2025 | 5,286 |
| ICLR | 2025 | 3,703 |
| EMNLP | 2025 | 3,214 |
| ACL | 2025 | 3,086 |
| ICML | 2025 | 3,046 |
| CVPR | 2025 | 2,871 |
| ICCV | 2025 | 2,701 |
| **ECCV** | **2024** | 2,387 |
| NAACL | 2025 | 1,193 |

**(venue, year) の組は9通りしかなく、2024年は ECCV だけである。**
したがって「年」という制約は「ECCV か否か」と等価であり、単独ではほとんど情報を持たない。
この性質が §2.2.4 の設計を決める。

### 2.2.2 索引

| | BM25 | 密ベクトル |
|---|---|---|
| 実装 | `bm25s` | FAISS `IndexFlatIP`（全走査の内積） |
| パラメータ | lucene, k1=1.5, b=0.75, stopwords=en, 語幹化なし | Qwen3-Embedding-8B, **4096次元**, fp16, max_tokens=8192 |
| prefix | — | doc `passage: ` / query `query: ` |
| サイズ | 5.1 GB | **42.0 GB**（2,564,545 × 4096 × 4 byte） |

どちらもチャンク単位である。**`IndexFlatIP` は全走査なので、取得件数 k が
そのまま計算量に効く**——この性質も §2.2.4 の設計を縛る。

### 2.2.3 クエリ分解と反復検索

質問を GPT-5.4 で **4本のサブクエリ**に分解する（固定）。

**本数を問題の型で振り分けない。**

- **設定**: 以前は single「1〜3個」/ multi「3〜6個」と分けており、その分岐のためだけに
  問題型の分類器が LLM を1回呼んでいた（本番入力に問題型が与えられないため）。
  分岐によって実際に何本増減したか、および分類器の精度を測った。
- **結果**: 買えていたのは平均 **0.58本**。分類精度は LLM **0.67** /
  ヒューリスティック **0.673** で差が無かった。
- **解釈**: LLM を1回余分に呼ぶ価値が無い。
- **設計**: 両者を挟む **4本**に固定し、分類器を経路から外した。

**プロンプトに入れる注記が2つある。**

**(a) 投げ先がローカル索引であることを明示する。**

- **設定**: 予測ファイルの実行ログから、生成されたサブクエリの文字列を集計した。
- **結果**: 再分解が作るサブクエリの **29〜41%** が `site:arxiv.org` / `filetype:pdf` の
  ような Web 検索演算子を含んでいた（55件中30〜39件のクエリが影響）。
- **解釈**: 投げ先は BM25 と FAISS なので、これらは**1件もヒットしない**。
  2周目・3周目の検索が丸ごと空振りしていた。
- **設計**: 「ローカル索引に投げるので演算子や URL は一切当たらない」旨をプロンプト先頭に
  置いた。分解でも再分解でも同じ注記を使う。

**(b) 属性制約が取れたらサブクエリの先頭に `[NAACL 2025]` を付けさせる。**
§2.2.1 のとおりチャンク本文がこの表記で始まるので、検索語として効く。
絞り込み自体は §2.2.4 が別に担当する。

**本数はプロンプトで頼むだけでなく、返り値も切る。**

- **設定**: 再分解の返り値には本数の指定が無かった。実際に生成された本数を集計し、
  さらに「あるサブクエリを1本抜いて候補列を組み直すと、`ecr@50` で拾えていた gold が
  減るか」を全812本について1本ずつ調べた（leave-one-out）。
- **結果**: 再分解は平均8.2〜9.3本・最大20本まで膨らんでいた。leave-one-out で
  gold が減ったのは **812本中5本だけ**であった（step0 4/180、step1 **0/305**、step2 1/327）。
- **解釈**: 膨らんだ分は検索力に寄与していない。一方コストは線形に増える
  （サブクエリ1本 = 検索1回 = reranker が `pool_k` 件を推論する量）。
- **設計**: 返り値を4本で切る。実際には合計458本に収まっている
  （step0 220 = 55×4、step1 126、step2 112）。

**反復の停止条件は読解 LLM の `sufficient` 判定のみ**とする（§2.3.2）。実測では
**55件中25件（45%）が上限より前で止まる**（1周22件 / 2周3件 / 3周30件）。

### 2.2.4 属性フィルタ（会議名・年）

質問が明示した会議名で検索結果を絞り込む。**索引の改修も再構築も不要**である
——検索結果のメタデータに既に venue/year が入っているので、各索引から多めに取ってから
落とすだけでよく、どの索引にも同じように効く。

**発火するのは会議名が一意に取れたときだけ**とし、次の場合は抽出せず従来と完全に同一の
コードパスを通す。

| 条件 | 理由 |
|---|---|
| 年しか書かれていない | §2.2.1 のとおり年単独は情報を持たない |
| `all venues` を含む | 実例の gold が iccv / neurips / icml にまたがっていた |
| 会議名が2種類以上見つかった | 引用先の会議名に引きずられるため |

年は**会議名に隣接する場合のみ**採用し、複数見つかったら使わない
（`Which CVPR 2025 papers cite UniAD (..., CVPR2023)` で CVPR2023 を拾わないため）。
**制約は元の質問から1回だけ取り、サブクエリには渡さない**（分解が会議名を落とすことがある）。

**取得件数の上限を上げてはいけない。**

- **設定**: 「絞り込み後に `per_index_k` 件残るように」と選択率から逆算する案を検討した。
  `per_index_k: 1000` に対し、NAACL（コーパス選択率 4.3%）で 34,560件を要求する設定である。
- **結果**: 密ベクトル検索の計算量が k に比例して跳ね上がる一方、取った34,560件は
  絞り込み後に `per_index_k` へ切られるので大半が無駄になる。
- **解釈**: 逆算した件数は、払う計算量に対して得るものが無い。
- **設計**: 上限を 3,000 に抑える。件数が足りなければ「絞り込み後10件未満なら
  絞り込みなしに戻す」フェイルオープンで戻るだけなので、小さく抑えるほうが正しい。

**発火状況の実測（検証55件）:**

| query | 抽出された制約 | gold |
|---|---|---|
| q_020 | NAACL 2025 | 4本 |
| q_022 | ICML 2025 | 3本 |
| q_023 | CVPR 2025 | 9本 |
| q_024 | **NeurIPS（年なし）** | 1本 |
| q_027 | CVPR 2025 | 1本 |

**発火は5件、その制約を満たす gold は 18/18 = 100%** であった。
q_024 で年が取れていないのは、上の「隣接する年のみ」という規則が働いた結果である。

### 2.2.5 融合とチャンク→論文

1本のサブクエリに対する検索は次の順序で進む。

1. 各索引が `per_index_k = 100` 件のチャンクを返す
2. **RRF で融合**（`k = 60`、重みは 1.0 : 1.0）

       s(c) = Σ_i  w_i / (60 + rank_i(c))

   **スコアではなく順位だけを使う。** BM25 スコアと内積はスケールが違って足せないためである。
3. 属性フィルタで絞り込む（§2.2.4）
4. `pool_k = 200` 件を Qwen3-Reranker-8B に渡す（§2.3.1）
5. 上位20チャンクをチャンクプールへ蓄積する（同一チャンクはスコアが高いほうを残す）

反復が終わったら、プールを論文のランキングに畳む。§1.5 で述べたとおり、
**論文の代表スコアは「表チャンクを除いた最大値」**とする。

    s(p) = max( { s(c) | c ∈ p,  chunk_type(c) ≠ table } ∪ { 0 } )

表チャンクは代表スコアに 0 として入るので、その種別しか候補に無い論文はスコア0で
最下位に沈む。ただし**候補列からは消えない**——ランキング B が押し上げれば戻ってくる。

**チャンクプールは変えない。** 表チャンクは読解 LLM にそのまま渡り evidence にも出せる。
これは次の2点による。

- gold の主要な根拠種別は **table が17件で最多**である（figure 15 / text_span 9 /
  citation_context 7 / equation_algorithm 7）。表を evidence から外すことはできない。
- 読解 LLM に表チャンクを見せたときと見せなかったときで、gold の根拠確認率は
  **71% 対 51%** であった。**読解には表を積極的に見せたほうがよい。**

順位付けには雑音でも、読解には最良の証拠になる——というのが表チャンクの性質である。
だから**代表スコアからだけ外し、プールには残す。**

### 2.2.6 ランキング B（論文→論文）

§1.3・§1.4 の設計方針を実装する部分である。
**起点（anchor）の近傍を、3種類の異なる「近さ」で引いて RRF 融合する。**
各ソース近傍100本、融合は `k = 60`。**GPU も LLM も使わない。**

| ソース | 近さの定義 |
|---|---|
| SPECTER2 | proximity 埋め込みの近傍（title+abstract） |
| 書誌結合 | 参考文献の arXiv ID 集合の Jaccard（共有2本以上） |
| 全文 MLT | 論文単位 BM25 への more-like-this |

**書誌結合は引用グラフではない。**

- **設定**: 当初は「A が B を引用している」関係でグラフを張ろうとした。
  anchor の参考文献からコーパス内の論文をどれだけ解決できるかを測った。
- **結果**: 解決できたコーパス内引用は **実測1本**であった。
  一方、共有する**古い文献**の Jaccard を測ると、TCM とそのピア3本で 0.19〜0.24、
  無作為に選んだ30本では中央値 0.000・最大 0.054 であった。
- **解釈**: コーパスは2024〜2025年しか無く、同時期の論文は互いに引用できない。
  引用リンクは張れないが、**同じ古典を引いているかどうかは強い信号になる。**
- **設計**: 引用ではなく**共有参考文献の Jaccard**（書誌結合）で近さを測る。
  「共有1本だけ」を切るのは、Adam や ResNet のような汎用引用で繋がってしまうためである。

**3ソースを併用する理由。**

- **設定**: ランキング B を外した候補列に対して、**候補50本に入らなかった
  gold** を各ソースが近傍100本の中に含むかどうかを数えた。起点は §2.2.7(d) と同じ
  「候補1位 ∪ 読解確認済み」である。
- **結果**:

  | | 根拠付き gold のみ | gold 全件（ピア込み） |
  |---|---|---|
  | 候補圏外の gold | 21本 | 41本 |
  | SPECTER2 | 18 | 35 |
  | 書誌結合 | 11 | 23 |
  | 全文 MLT | **20** | **37** |
  | 3ソースの和 | 20 | 40 |

- **解釈**: **回収の集合としては全文 MLT がほぼ他を包含する**（根拠付き gold では
  和20 = MLT 単独20）。つまり「違う gold を拾うから併用する」という説明は成り立たない。
  それでも3ソースを使うのは、**複数ソースに支持された論文が RRF で上位に来る**
  という順位融合の効果による。実際、単体ソース・2ソースの構成は、試した4つの検索構成
  すべてで3ソース構成に劣った。
- **設計**: 3ソースを等重みで RRF 融合する。

**ランキング B を reranker に通さない。** reranker は「質問に答えるか」で判定するので、
質問文が名指ししないピア gold を必ず下げる。B をそこに晒さないことが、
§1.3 の問題に対する答えそのものである。

### 2.2.7 A/B の順位融合

    score(p) = w_A / (k + rank_A(p)) + w_B / (k + offset + rank_B(p))
    k = 10,  w_A = w_B = 1.0,  offset = 0

上位50本で切って `candidate_papers` とする。

**スコアではなく順位だけを使う。**

- **設定**: 当初は reranker のスコアと近傍の類似度を直接足して混ぜていた。
- **結果**: cr@20 が **0.822 → 0.773** に落ちた。
- **解釈**: reranker の yes 確率と近傍の仮スコアはスケールが違い、足すと一方が支配する。
- **設計**: 順位しか見ない RRF にする。この問題は構造的に起きなくなる。

設計上の要点が4つある。

**(a) 統合には「50本で切る前の全長」をランキング A に使う。**
51位の論文を B が強く推していても、先に切ると押し上げようがないためである。

**(b) anchor 自身をランキング B の先頭に置く。**

- **設定**: 各ソースは anchor を自分の近傍から外す（自分自身は返さない）。
  この状態で融合したときの single_paper の挙動を調べた。
- **結果**: **gold そのものだった候補1位が top20 から消えた事例が2件**あり、
  single の cr@20 が **1.000 → 0.923** に落ちた。
- **解釈**: anchor は A の `1/(k+1)` しか持てないのに対し、「A にも B にも居る」論文は
  2項ぶん得るので、軒並み抜かれる。
- **設計**: anchor 自身を B の1位に置く。論文は自分自身に最も近いので、
  定義としても自然である。

**(c) 融合定数を `k = 10` にする。**

- **設定**: k は「リスト内の順位」と「両方に載っていること」のどちらを重く見るかを決める。
  A の1位（B に無い）は `1/(k+1)`、A でも B でも r 位（0起点）の論文は `2/(k+1+r)` を得るので、
  後者が前者に勝つ条件は

      2/(k+1+r) > 1/(k+1)   ⟺   r < k+1

  である。この閾値がリスト長（50本）に対して妥当かを検討し、
  さらに k を振って、融合後 top5 の出所を4つの検索構成で数えた。
- **結果**: **k=60 だと閾値が `r < 61` になり、リスト長50本では「A と B の両方に
  載っていればどれだけ深くても A の1位に勝つ」**ことになる。実際に、
  reranker が1位に置いた論文が A の40位 × B の40位の論文に抜かれていた。

  | k | A の上位5位 | A の6位以下 | B にしか無い | top5 の gold 率 |
  |---|---|---|---|---|
  | 60 | 49〜54% | 38〜45% | 5.5〜8.0% | 25.8〜27.6% |
  | **10** | **56〜62%** | **26〜35%** | **9.1〜12.0%** | **26.9〜29.1%** |

- **解釈**: k を下げると減るのは「A の中位 × B の中位の合わせ技で浮上した論文」だけ
  （-12pt）で、**A の上位（reranker が本気で推した論文）と B 単独の上位（近傍1位）は
  どちらも増える**。top5 の gold 率も上がっている。
- **設計**: `k = 10` にする。「両方の**上位**に居るときだけ勝つ」という本来の意味になる。

**(d) 起点を「候補1位 ∪ 読解 LLM が根拠を確認した論文」に広げる。**

- **設定**: 読解 LLM は本文を読んだうえで根拠のある論文を返すが、その結果は
  順位付けに一度も使っていなかった。これを B の起点に加えた場合を、
  4つの検索構成と、ランキング A を打ち切らずに使った条件の計5条件で測った。
- **結果**: **multi@10 が5条件すべてで +0.030〜+0.082**。single の cr@1 は5条件とも不変。
  一方、LLM が確認した論文の gold 率は 68本中52本 = **76%** で、
  候補1位の 85%（47/55）より**低い**。
- **解釈**: **効いているのは判定の精度ではなく起点の本数である。** anchor が1本だと
  展開できるトピッククラスタも1つなので、§1.4 の「3本目以降が沈む」が埋まらない。
  なお起点が2本以上になるのは55件中16件で、**うち14件が multi_paper** である
  ——single に副作用が出ないのはこの偏りによる。
- **設計**: 和集合を起点にする。**候補1位は必ず残す**——LLM 確認済みだけにすると
  候補1位が B の先頭から外れ、single の cr@1 が 0.923 → 0.885 に落ちる（(b) と同じ事故）。

## 2.3 Reranker

本システムの並べ替えは2段ある。**チャンク単位のニューラル reranker**（Qwen3-Reranker-8B）と、
**論文単位の LLM 判定**（GPT-5.4）である。前者はランキング A の内部を、
後者はランキング B の起点を通じて、それぞれ順位に効く。

### 2.3.1 Qwen3-Reranker-8B（チャンク単位）

| | |
|---|---|
| モデル | `Qwen/Qwen3-Reranker-8B`, fp16, max_tokens 2048 |
| 入力 | RRF 融合後の上位 `pool_k = 200` チャンク |
| 出力 | **順位を完全に置き換える**（上位20チャンクをプールへ） |

Qwen3-Reranker は causal LM ベースの yes/no 判定型で、**"yes" トークンの確率**を
スコアにする。指示文は次のとおりである。

> Given a scientific question, retrieve passages from research papers that
> help identify or support the answer

### 2.3.2 GPT-5.4 による読解判定（論文単位）

Azure OpenAI の GPT-5.4（`reasoning_effort: medium`、`max_completion_tokens: 16000`）に、
上位20論文 × 論文あたり2チャンク（各1,800文字）を読ませ、3つを返させる。

| 返り値 | 役割 |
|---|---|
| `paper_ids` | 根拠を確認できた論文。**提出には使わない**が、**ランキング B の起点になる**（§2.2.7(d)） |
| `evidence_chunk_ids` | 根拠チャンク。evidence 出力そのもの |
| `sufficient` / `missing` | **反復の停止条件**と、次の再分解の材料 |

**停止条件を「見つかった論文の本数」にしてはいけない。**

- **設定**: 以前は「規定の本数の論文が見つかったら止める」設計だった。
  実際に何周目で止まっているかを調べた。
- **結果**: 検索は毎回20件の候補を返すので、**初回の時点で条件を満たしてしまい**、
  反復が1周も回らなかった。
- **解釈**: 本数は検索の設定で決まる量であり、質問に答えられるかどうかとは独立である。
- **設計**: 停止条件を LLM の `sufficient` 判定のみにする。本番入力に問題型が
  与えられないこととも整合する。

**この LLM 判定は「もう一段の reranker」として働く。** ただし §2.2.7(d) で見たとおり、
**判定の精度は候補1位より低い（76% 対 85%）**。それでも効くのは順位の精度ではなく
**展開の起点を増やす**ためであり、伸びは @10 に集中する。

## 2.4 出力

```
candidate_papers : 上位50本の paper_id（順位そのまま）
evidence         : 読解 LLM が指名したチャンク
```

**提出論文の選定と回答生成は行わない。** 候補列の順位をそのまま渡し、
どれを提出するか・どう答えるかは読解チームが決める。

# 3. Experimental Results

## 3.1 実験設定

**検証データ**: 55問（single_paper 26 / multi_paper 29）。
gold 論文146本（うち根拠付き117本、ピア29本、1クエリあたり中央4本・最大9本）。
evidence の注釈は149件（1クエリあたり中央2件・最大9件）。

**本番データ**: 71問（multiple_choice 50 / table 21、freeform は0件）。**gold は無い。**

**指標**: §1.2 で述べた `candidate_recall@k`（cr@k）と
`evidence_candidate_recall@k`（ecr@k）。どちらもクエリごとに計算してマクロ平均する。
根拠付き gold が1本も無いクエリは ecr の分母が空になるので集計から除外する。

**投入方法**: 本番入力の形に揃える。検証データにだけ存在するフィールド（問題型など）は
落として投入する。与えたまま評価すると「正解を教えてもらった状態」の点数になるためである。

**比較の作法**: LLM は非決定的でクエリは55件しかないため、数ポイントの差はノイズの
可能性がある。**§3.3 だけは、同一の検索結果から候補列の組み立てだけをやり直した対照**
なので、LLM のばらつきを含まない。

## 3.2 Validation set での性能

### 全体

本システムは **multi_paper の cr@20 で 0.8592、ecr@20 で 0.9253** に達する（表 3.9.1）。

**single_paper は @5 以降で飽和している**（cr = 1.000）。したがって
**打ち手の効きは multi にしか乗らず**、総合だけを見ていると改善が半分に薄まる。
以降のアブレーションを multi 中心に読むのはこのためである。

### 深い順位では天井に近い

- **設定**: 本システムの候補列（上位50本）に根拠付き gold 117本がどれだけ入っているかを
  micro で数え、あわせて「そのクエリの gold を1本残らず拾えた率」（All-Gold）を測った。
- **結果**: **@50 で 115/117（欠落2本）**、@20 で 110/117。欠落2本はいずれも
  multi_paper のクエリで、q_025 の `neurips2025_02748` と q_051 の `eccv2024_01567` である。
  All-Gold は根拠付き gold で **0.9636（53/55）**、公式 gold で **0.8727（48/55）**であった。
- **解釈**: **根拠付き gold については、検索プールの上限にほぼ到達している。**
  残る伸びしろは公式 gold の All-Gold にあり、未達7クエリのうち5つはピア gold の
  取りこぼしである。

## 3.3 ランキング B を外す

これが本システムの中心的な主張に対応する対照実験である。

- **設定**: **A/B 融合を通すか通さないかだけ**を切り替えて候補列を組み直した。他の条件（サブクエリ、検索結果、
  読解結果）は完全に同一で、融合ありの側は
  **通常どおり走らせた候補列と55件すべて完全一致する**ことを確認してある。
- **結果**: multi_paper で **ecr@20 が 0.7356 → 0.9253（+0.190）**、
  @10 が 0.6590 → 0.8391（+0.180）（表 3.9.2）。
  top20 に入った gold を実数で数えると、**B が足す32本のうち18本（56%）は根拠付き gold**
  であった。**single は全 k で完全に一致**する。**@1 も完全に同値**である。
- **解釈**: `ecr` はピア gold を分母から完全に除いた指標なので、**この改善は
  「ピアを拾ったことによる見かけの改善」ではない**。B は §1.4 で見た
  「沈んだ2本目・3本目」を引き上げている。@1 が動かないのは、
  §2.2.7(b) で anchor を B の先頭に固定しているため候補1位が必ず1位のまま残る設計による。
  single が不変なのは §2.2.7(d) のとおり、起点が2本以上になるクエリの大半が multi だからである。
- **補足**: 別の検索構成でも同じ向きで、multi ecr@20 は 0.6944 → 0.8994（+0.205）であった。

## 3.4 A/B 融合まわりの設定

- **設定**: A/B 融合を導入したあと、3つの改良を順に積み、それぞれ検証55件を通した。
- **結果**: multi ecr@20 が **0.8554 → 0.9080 → 0.9253** と単調に上がった（表 3.9.3）。
- **解釈**: 2番目のステップは3つの変更（融合定数 `k=60→10`、近傍 50→100本、
  起点の拡張）をまとめて入れている。融合定数と近傍は**セットでしか効かない**
  （片方だけでは改善しない）ためで、起点の拡張は候補列の組み直しで先に確かめてから
  同時に載せた。そちらでは融合定数と近傍だけで multi ecr@20 が
  0.871 → 0.910、そこに起点拡張を足して 0.914 まで伸びる。
  3番目（表チャンク除外）は §1.5 の設計で、**single は cr@1 から cr@50 まで
  1桁も動かない**。

## 3.5 検索エージェントを外す

- **設定**: 検索構成を固定したまま、**分解・反復・読解を走らせず生の質問1本で検索**した
  構成と比較した。この構成では候補列の並べ替えだけで完結する部分（A/B 融合と
  表チャンク除外）のみを載せ、**LLM を1回も呼ばない**。
- **結果**: **@20 以降はほぼ互角**で、cr@50 は 0.9591 で**完全に一致**した。
  **@1 はエージェント抜きのほうが上**（ecr 0.6369 対 0.6051）、
  **@5 だけエージェントありが 0.067 上回る**（表 3.9.4）。
  一方エージェント抜きは **LLM 呼び出しが 0 回**である（エージェントありは最大6回/クエリ）。
- **解釈**: 差の出所は2つしかない——**サブクエリ4本の融合**と、**ランキング B の起点**
  （エージェント抜きでは読解が無いので候補1位だけになる）である。
  @1 で逆転するのは、**分解した4本が元の質問の語の組み合わせを保たない**ためで、
  実際に step0 のサブクエリに質問文そのものが入るのは **0/55件**であった。
  **LLM エージェントが稼いでいるのは @5〜@10 の帯だけで、深い集合（@20〜@50）は
  エージェント無しでもほぼ同じところに到達する。**

## 3.6 索引の粒度

- **設定**: 埋め込みも reranker もエージェントも使わない条件で、BM25 の索引単位だけを
  変えて比較した（チャンク単位 / 論文単位 / 両方の RRF 融合）。
- **結果**: **論文単位 BM25 が chunk BM25 単体より強い**（ecr@20 で 0.825 対 0.797、
  ecr@50 で 0.865 対 0.847）。両方を融合すると @5 が最良になる（表 3.9.5）。
- **解釈**: 質問語が論文内の離れた場所に分散していると chunk 側は弱くなり
  （1チャンクに語が揃わない）、逆に論文単位は表の1セルのような局所的な根拠が埋もれる。
  **現行構成は chunk BM25 しか使っていないので、ここは未回収の伸びしろである。**

## 3.7 読解判定が得られないクエリ

読解 LLM の判定は、順位付けの側でも使っている——§2.2.7(d) のとおり
**ランキング B の起点**になる。その判定が返らないクエリでは起点が候補1位だけに戻るので、
判定の取得率そのものが検索性能に効く。

- **設定**: 各クエリについて、読解 LLM から使える判定が1度でも返ったかを数えた。
- **結果**: **55件中9件で一度も返っていない**
  （q_002 / q_003 / q_005 / q_007 / q_008 / q_019 / q_037 / q_049 / q_055）。
  候補は毎回20件渡っているので、候補が空だったのではなく返答が使えなかった。
- **解釈**: この9件ではランキング B の起点が候補1位だけに戻るので、
  **§2.2.7(d) の起点拡張が実際に効いているのは 46/55 件**である。
  §1.4 で述べた「2本目以降を掘る」力が、16%のクエリでは半減している。

## 3.8 Test set での性能

**本番71問には gold が無いため、recall を測ることはできない。**
したがって以下は候補列の記述統計と、2構成の間の一致度である。

- **設定**: 同じ検索構成で、エージェントありとエージェント抜きの2つを通した。
  両者の候補列を突き合わせ、一致度を測った。
- **結果**: どちらも**全71件で候補50本が埋まり**、メタデータからタイトルを引けなかった
  候補は0件であった。エージェントありでは evidence が140件付き、
  **evidence が1件も出せなかったクエリは1件だけ**であった。
  一方で、**候補列が完全に一致したクエリは0件**、top50 の集合の Jaccard は中央 **0.37**、
  **片方にしか居ない論文が半分近くを占めた**（表 3.10.2）。
- **解釈**: 検証データでは両者の ecr@20 がほぼ互角（0.9576 対 0.9606）であったが、
  **それは「同じ論文を拾っていた」からではなく「違う論文を拾って同じくらいの点に
  なっていた」**ということになる。また、検証データでは evidence 0件のクエリが9件
  （16%）あったのに対し本番では1件（1.4%）であり、**本番のほうが読解が安定して
  働いている**。
