# 熊谷さんの検索システム（`docs/kumagai.md`）を読んでの考察

**元資料**: `docs/kumagai.md`（熊谷さんの検索システム仕様 + アブレーション結果、2026-08-11 時点）
**書いた日**: 2026-08-13
**比較対象**: 我々の `agentless/agentless`（LLM ゼロ）と `reading_expand_rrf/notable`（フル走行）

向こうも**検索エージェントなし**で、同じ MinerU コーパス（27,487論文）・同じ validation 55問を
使っている。つまり**土俵が揃っている珍しい比較対象**なので、数字をそのまま並べたくなるが、
**そのままでは並べられない**。まずそこから。

---

## 1. 数字を同じ土俵に載せる — **gold 定義で最大9pt動く**

`kumagai.md` の809行目に、**同じランキングを3つの gold 定義で測った値**が書いてある。
これが両者を突き合わせる唯一の鍵になる。

| gold 定義 | 熊谷 @50 | 我々 `agentless` @50 | 我々 `notable` @50 |
|---|---|---|---|
| 公式 gold | 0.9091 | **0.9591** | **0.9591** |
| evidence-backed | 0.9545 | **0.9788** | **0.9894** |
| Answer-bearing（87本） | 1.0000 | 未測定 | 未測定 |

**@50 では我々が上**（公式 gold で +5.0pt、evidence-backed で +2.4pt）。
向こうの `Recall@20 = 1.0000` は **Answer-bearing gold 87本**の話で、我々の分母とは別物。

我々の validation gold を数え直すと（`data/validation.jsonl` の実測）:

    gold 合計 146本 / 根拠付き 117本 / 根拠なし 29本

熊谷さんの Answer-bearing 87本は、**我々の evidence-backed 117本よりさらに絞った集合**
（「回答に必要な論文だけ」）。同じランキングでも定義を緩めるほど数字が下がるので、
**87本で 1.0000 は 117本で 1.0000 を意味しない。**

### @1〜@10 は向こうが明確に上

| k | 熊谷（Answer-bearing 87本） | 我々 `agentless`（ecr） | 我々 `notable`（ecr） |
|---|---|---|---|
| 1 | 0.7808 | 0.6369 | 0.6051 |
| 5 | 0.9323 | 0.7747 | 0.8419 |
| 10 | 0.9848 | 0.8889 | 0.9152 |
| 20 | 1.0000 | 0.9576 | 0.9606 |
| 50 | 1.0000 | 0.9788 | 0.9894 |

定義の差を @50 で観測された分（Answer-bearing → evidence-backed で **約 -4.5pt**）で
割り引いても、向こうの @10 は evidence-backed 換算で **0.94 前後**と推定され、
我々の 0.889 / 0.915 を上回る。**この換算は @50 の1点から外挿した粗い推定**なので、
確定させるには向こうの Answer-bearing 定義を貰って我々の列を測り直す必要がある（§7）。

いずれにせよ、CLAUDE.md がずっと書いてきた
「**@5 で外部チームに 0.145pt 離されている**」が、独立した資料で追認された形になっている。

### 結論

**二つのシステムは強い場所が反対。** 向こうは浅い順位（@1〜@10）が急峻、
我々は深い集合（@20〜@50）が厚い。**足し算になる余地が大きい。**

## 2. なぜ形が違うのか — 設計の対応関係

| | 熊谷システム | 我々 | 評価 |
|---|---|---|---|
| 論文単位の集約 | **chunk BM25 と paper BM25 を論文単位に畳んでから RRF（1論文1票）** | チャンク単位で RRF → `to_gold_papers(agg=max)` で最後に畳む | **最大の差** |
| 上位論文の活用 | Seed Expansion（1位論文の語彙を**質問に連結**して再検索） | ランキングB（1位論文に**似た論文**を埋め込み・書誌結合・MLT で引く） | 別物。併用可能 |
| reranker | 元順位 0.52 : Qwen 0.48 の**順位融合** + Top20 集合保護 | **純置換**（既定） | 我々に `rerank_blend` 実装済み・未測定 |
| reranker のモデル | 4B | 8B | 向こうの実測では 8B < 4B |
| 提出本数 | Paper Selector が決める | 決めない（読解チーム担当） | 担当分界の違い。触らない |

### 「1論文1票」が効く理由は我々の側でも説明が付く

CLAUDE.md の「**表チャンクが論文の代表スコアを壊す**」と同根の問題。
チャンク単位で融合すると、長い論文・表が多い論文が候補列を占有する。
我々は `paper_score_skip_chunk_types: [table]` で**症状の一部**を抑えたが、
**融合の段階では依然チャンク単位**のまま。

向こうの寄与分析ではこの1点だけで:

| Paper BM25 + 論文単位RRF | 差分 |
|---|---|
| Recall@1 | **+9.34pt** |
| Recall@5 | **+8.43pt** |
| Recall@10 | +1.52pt |
| Recall@20 | +1.11pt |

**向こうの改善の中で最大**。しかも効き方が @1/@5 に集中していて、我々の弱点と正確に重なる。

### reranker のモデルサイズ

向こうの実測（Answer-bearing gold）:

| モデル | Recall@1 | Recall@10 | 秒/問 |
|---|---|---|---|
| 0.6B | 0.7202 | 0.9808 | 2.24 |
| **4B** | **0.7808** | **0.9848** | 7.15 |
| 8B | 0.7581 | 0.9763 | 9.22 |

**8B は 4B より悪い。** 我々は 8B を主力にしていて、索引構築に4GPUで約31時間かけている。
ただし向こうは**論文代表テキストの先頭2,000文字**を渡す論文単位 rerank で、我々の
`qwen3`（チャンク単位）とは入力の作りが違う。**そのまま「8B をやめろ」とは読めない**が、
`qwen3_paper`（論文単位、実装済み）との組み合わせでは追試する価値がある。

## 3. 移植候補（優先順）

### Tier 1 — 安く、agentless にも agent ありにも同じように効く

#### (1) Paper BM25 を A に足す + 論文単位 RRF

我々は `bm25s_paper` 索引を**構築済み**で、`configs/search_style/bm25_dual_qwen3_8b_rerank_qwen3_8b.yaml`
も**すでに存在**する（追加構築ゼロ）。CLAUDE.md の純 BM25 ablation でも向きが一致している:

| 構成 | recall@5 | ecr@5 | ecr@20 |
|---|---|---|---|
| `bm25`（chunk のみ） | 0.606 | 0.697 | 0.797 |
| `bm25_paper`（論文単位） | 0.634 | 0.723 | **0.825** |
| `bm25_dual`（両方 RRF） | **0.663** | **0.748** | 0.815 |

**ecr@5 で +5.1pt。**

⚠ **索引を足すだけでは半分。** 向こうの効き目の本体は「**論文単位に畳んでから RRF（1論文1票）**」で、
これは `RRFFuser` を論文単位で動かす小改修が要る。**A の作り方を変える打ち手なので、
B や統合層とは独立に効くはず。**

#### (2) `rerank_blend` を有効にする（実装済み・未測定）

向こうの実測「**Qwen 順位だけを使うと Recall@1 が 0.9848 → 0.7045 に落ちる**」は、
我々が既定でやっている純置換に対する直接的な反証。

我々には `rerank_blend`（`original_weight` / `rerank_weight` / `protect_top`）が
**実装済みで yaml 1枚で測れる**。向こうの値は **0.52 : 0.48**、`protect_top` は 20。

CLAUDE.md の「重みを借りるな、振って選び直せ」「cr と ecr を並べて読め」はそのまま適用する。

#### (3) Seed Expansion（LLM ゼロの pseudo relevance feedback）

    expanded_query = 元質問 + 1位論文のタイトル + paper BM25 文書の先頭512字

これを初回順位と RRF する（`1/(60+initial_rank) + 1/(60+expanded_rank)`）。

**我々の `rewrite.yaml`（検索結果に接地したクエリ書き換え）が狙っていたものの LLM 抜き版。**
rewrite が失敗した原因は CLAUDE.md のとおり「LLM が B の論文のタイトルをそのままクエリにして、
すでに持っている論文を引き直しただけ」（候補列のタイトル語を8割以上含むサブクエリが
1% → 16% に増えた）。**機械的な連結ならその失敗モードが構造的に起きない**
——連結先が元質問なので、質問の語が必ず残る。

向こうの実測:

| Seed Expansion | 差分 |
|---|---|
| Recall@5 | **-2.88pt** |
| Recall@10 | +1.92pt |
| Recall@20 | +2.93pt |
| All-Gold@20 | +3.64pt |
| multi の Recall@20 | **約 +13.4pt** |

@5 が下がるので、**`rerank_blend` の Top20 保護と組み合わせる前提**。

### Tier 2 — エージェントありの構造変更（§4）

### Tier 3 — test 固有・条件付き

#### (4) Exact Method Search

質問が一意な手法名を書いていて、その論文が候補外なら**末尾に**足す（最大5本、上位昇格なし）。

我々は同じものを `title_protect` として実装し、**効果ゼロで削除した**。理由は
「名指しされた28本が**全部すでに候補1〜4位に居た**」から（抽出自体は 28/28 = 100%・誤検出0）。

ただし向こうは「**予想 test では AD-GS を候補外から4位へ救った**」「Exact を外すと
AD-GS が Top50 圏外へ消えた」と書いている。**validation で冗長だったものが test で効く**
典型例で、§6 の論点に直結する。抽出精度は実証済みなので、**保険として戻す価値はある**
（コストは候補列の末尾5本だけ）。

#### (5) Structured Filter（会議 + 年 + 表/図/数式の種類が全部明示された open-set 質問だけ発火）

我々の `attribute_filter` は会議名だけで、**modality（表・図・数式）での絞り込みが無い**。
`chunk_type` は持っているので実装は軽い。向こうの実測は @10 +1.11 / @20 +0.66 /
All-Gold@20 +3.64 / @5 -0.20。

ただし**本人が「test では0件発火」と書いている**ので優先度は下げる。

#### (6) Method Dense Tail は移植しない

向こう自身が**削除候補**と結論している（全 cutoff で改善0、23問の候補集合を変えるが
Answer-bearing gold の回収に貢献なし。外すと候補生成が65%速くなる）。

⚠ **これを我々のランキングB の否定として読んではいけない。** 向こうのは
「手法 owner 論文の SPECTER2 近傍を**3本 tail に足す**」もので、我々のは
「3ソース融合の**順位融合**」。規模も役割も違う。我々の実測
（B を外すと multi ecr@20 が **-0.190**）と矛盾しない。

## 4. 検索エージェントありへの組み込み — **`kumagai.md` §3 がほぼそのまま設計案**

向こうの推奨は「**クエリ分解を検索器の内側へ混ぜ込まない**」で、具体形は:

```
anchor lane（元質問）      : Seed Expansion あり
subquery lanes（分解結果） : chunk BM25 + paper BM25 のみ、Seed Expansion なし、rerank なし
        ↓ 論文単位の multi-query RRF
        score(p) = 1.0/(60+anchor_rank) + Σ (1/N)/(60+subquery_rank_i)
        ↓
Qwen reranker を**元質問で1回だけ**
```

我々の現行との差分は**3つだけ**で、どれも既存機構の延長線上にある。

### 差分A: anchor lane が無い

`_decompose()` が作る4本に元質問は **0/55 件**しか入らない。
我々はこれを `rawq_pin`（元質問を step0 に5本目として足し、その1位を A の先頭に**固定**）
として部分実装済みで、**ecr@5 が土台7本すべてで +0.009〜+0.026**だった。

熊谷案はもっと強く、**元質問を重み 1.0 の独立レーンとして融合する**
（サブクエリ群の合計と同じ重み）。`rawq_pin` は1本ピン留めするだけなので @1 しか
動かせないが、**レーン化すれば @5〜@20 まで効く**。実装も既存の `_rawq_ranking()` の
再利用で済む。

⚠ CLAUDE.md の警告がそのまま効く: **生質問1本の ecr@1 は 0.637 で頭打ち**なので、
土台自身の @1 がそれを超える構成では @1 が下がる。**重み 1.0 固定にせず振る。**

### 差分B: サブクエリ本数でスコアが膨らむ

向こうの `1/N` 正規化は、CLAUDE.md の
「**サブクエリを増やすほど良くなる関係になっていない**（812本 → 461本に絞っても指標が落ちない）」
という実測に対する、**我々が持っていなかった説明と対処**。

`subquery_merge: rrf` は正規化していないので、サブクエリを多く作った質問だけ裾が厚くなる。
ここに `1/N` を入れるのは1行。

### 差分C: reranker がサブクエリごとに走っている

**これがいちばん大きい。**

我々は 4本 × 最大3周 = **最大12回**、毎回 `pool_k` 件を 8B で推論している。
向こうは融合後に**1回**。

速度だけの話ではない。CLAUDE.md が認識している
「**サブクエリ間の reranker スコアは比較可能でない**」（`subquery_merge: max` の問題）が、
**融合を先にして rerank を後に1回やれば構造的に消える。**

我々には `pool_rescore`（プール全体を元質問で1回リランク）が実装済みで、
**これが熊谷案の「Qwen を元質問で1回だけ」そのもの**。CLAUDE.md には
「`subquery_merge` と `pool_rescore` を同時に有効にするな」と書いてあるが、それは
**両方が順位を作って後勝ちになる**からで、熊谷案は**サブクエリ lane でそもそも rerank しない**
ので競合しない。**「lane 内 rerank を切る」オプションを足せば両立する。**

### 組み込み後の姿（案）

```
元質問 ──┬─ anchor lane: BM25(chunk) + BM25(paper) + Seed Expansion   [rerank なし]
         └─ LLM 分解 4本 ─ 各 lane: BM25(chunk) + BM25(paper) + 埋め込み [rerank なし]
                    ↓ 論文単位 multi-query RRF（anchor 1.0 : サブクエリ計 1.0）
                    ↓ 属性フィルタ
              Qwen3-Reranker を**元質問で1回だけ** + rerank_blend（0.52:0.48, protect_top 20）
                    ↓ ランキングA（切る前の全長）
              A/B の RRF 統合（現行の B はそのまま）
                    ↓
              candidate_papers + evidence（読解ループは現行どおり）
```

**recall が上がる根拠は3つ重なる**:

1. A の浅い順位が Paper RRF と anchor lane で厚くなる
2. B は現行のまま深い集合を保つ
3. rerank が1回になるぶん、`pool_k` を広げるか反復を増やす余裕が出る

## 5. 向こうが持っていて我々が持っていないもの / その逆

| | 熊谷 | 我々 |
|---|---|---|
| 論文単位 RRF（1論文1票） | ○ | **×** |

## 6. `test_inputs.jsonl` の性質が結論をどう変えるか

本番71件は `data/test_inputs.jsonl`（2026-08-13 に HF から取得）。
validation とは性質が違い、それが**打ち手の優先順位を変える**。

### (a) 熊谷さんは test 71問の pseudo-gold を持っている

`kumagai.md` 854行以降。全機能ON で:

| | Recall@10 | Recall@20 | Recall@50 | All-Gold@20 |
|---|---|---|---|---|
| validation | 0.9682 | **1.0000** | **1.0000** | **1.0000** |
| **test 71問** | 0.8991 | **0.9460** | 0.9953 | **0.8873** |

**test は validation より明確に難しい。**

### (b) validation で飽和していた指標が test では飽和しない

我々は「`single_paper` の cr@20 = 1.000 で飽和済みだから**打ち手は multi にしか乗らない**」を
すべての判断の前提にしてきた。**test でこれが崩れるなら、@1〜@10 を上げる打ち手
（Paper RRF / anchor lane / rerank_blend / Seed Expansion）の価値は validation で
測った値より大きい。**

逆に、我々が「効果ゼロ」と判定して**削除した機構が復活しうる**。`title_protect`
（= Exact Method Search）はその筆頭で、向こうの test では AD-GS を救っている。

### (c) アノテーションが雑でないなら、ランキングB の相対価値は下がる

B は「質問文が名指ししていない同トピックのピア論文」（validation では gold 146本中
**29本 = 20%**）を拾うために入れた機構。test の質問は具体的で
（「report the edge-device inference speedups reported for … and the approximate
RTDETRv2 fine-tuning wall-clock time」）、**答えるのに必要な論文だけが gold になっている
可能性が高い。**

⚠ **ただし B を外す判断はしない。** `docs/best_configs.md` §6.1 の対照実験では、
**B が top20 に足す32本のうち18本（56%）は根拠付き gold**で、ピアを完全に分母から
除いた ecr でも multi @20 が **+0.190** ある。B は「沈んだ2本目・3本目の gold を
引き上げる」機構でもあるので、ピアが減っても効き目の過半は残る。
**相対的に A 側の打ち手を優先する、という読み替えに留める。**

### (d) 回答タイプの構成

| answer_type | 71件中 |
|---|---|
| multiple_choice | 50 |
| table | 21 |
| freeform | **0** |

**table が30%**あるので、表チャンクの扱い（**代表スコアからは外すが読解には見せる**）は
validation 以上に効く可能性がある。

## 7. 評価の段取り

**問題: test に gold が無いので、打ち手の採否は validation でしか測れない。**
その validation は single が飽和していて、まさに今回効きそうな打ち手が見えにくい。
抜け道は2つ。

1. **熊谷さんの test pseudo-gold を借りる**（最短）。向こうは71問で ablation を
   回した実績があるので、同じ疑似 gold で我々の候補列を採点すれば **test 上で直接比較できる**。
   gold 定義（Answer-bearing / evidence-backed / 公式）も揃えて併記してもらう。
2. **validation を Answer-bearing 87本の定義で測り直す**。我々の
   `evidence_backed_paper_ids()` は117本ベースなので、向こうの87本の定義を貰えば
   同じ列を出せる。**指標の互換性はここでしか作れない。**

### オフライン再生は今回は使えない

CLAUDE.md の「統合まわりはオフラインが本評価」は**この節の打ち手には適用できない**。
Paper RRF も anchor lane も Seed Expansion も **A の作り方そのものを変える**ので、
候補列からの再生では測れず、フル走行か `eval_retrieval.py` 相当が要る。

幸い **agentless 経路なら LLM ゼロで約1時間**（本番71件の実測で索引ロード16分 + 検索41分）。
**Tier 1 の3つはどれも LLM を使わないので、agentless の土台で先に篩えるのが安上がり。**
