# LitTraceQA 改稿版4：数値を除く再レビュー

## レビュー範囲

本レビューでは、ユーザーの指定に従い、**これから実施する実験の値や未確定の比較結果は評価していません**。以下では、初見の査読者が読む際の主張の一貫性、方法記述の明確さ、評価設計のスコープ、再現性、関連研究、未実施事項の扱いだけを確認しています。

## 総評

今回の改稿は、これまでで最も論文らしい骨格になっています。前回までの「なぜこの構成を最終構成と呼ぶのか」という問いに対し、候補50本を下流が順位で切らずに利用するという**実際の運用上の目的関数**を明示したことは、非常に重要な改善です。また、疑似コードを追加して検索・属性フィルタ・論文単位融合・rerank・チャンクプール・Verifier・A/B融合の順序を固定したことで、査読者が実装を頭の中で追えるようになりました。

さらに、`evidence 未注釈 gold` の解釈を慎重に保ち、中心アブレーションが Base 構成上であること、外部ベースラインが未測定であること、最終構成での再構成実験が未実施であることを隠さず書いています。これは誠実であり、数値が揃った後に論文としての信頼性を作る良い基盤です。

残る重要点は、実験値の良し悪しではなく、**Evidence を正式な出力に含めるならその品質を誰が評価するのか**、および**疑似コードと本文の例外処理が完全に整合しているか**です。ここを直すと、数値が未完成の段階でも、論文の方法論はかなり堅牢に見えます。

## 最優先で直すべき、数値非依存の論点

### 1. Evidence を「正式な出力」とするなら、品質評価を後段に完全移管することはできない

*§1.1 と §3.5 は、システムの出力を「候補論文50本の順位列 ****と**** Verifier が指名した根拠チャンク」と定義しています。しかし §4.2 は、evidence precision / recall / F1 を報告しない理由として、根拠の品質評価は後段の責務であると述べます。*

*この二つは、初見の査読者には矛盾して見えます。****論文が evidence を出力物として主張するなら、その evidence が適切かを少なくとも何らかの形で評価する*****必要があります。** 最終回答生成を扱わないことと、evidence extraction / verification の品質を評価しないことは別問題です。

ここは、次のどちらかへ明確に寄せることを勧めます。

| 選択肢 | 原稿での一貫した位置付け | 必要な変更 |
| --- | --- | --- |
| **A. retrieval-only に絞る** | 正式な出力は候補論文順位列のみ。Verifier は反復停止・anchor選択に使う内部的な制御信号 | §1.1、§3.1、§3.3、§3.5 の「evidence を出力する」記述を「内部で保持する根拠候補」へ変更する |
| **B. evidence も本稿の出力に含める** | 回答生成は対象外だが、根拠候補の同定は本稿の責務 | evidence の定義、照合規則、品質指標、失敗例を補助表として報告する |

現在の骨組みは A と B の中間にあります。ランキング B の anchor に使うというだけなら A が自然です。一方、コンペの提出仕様が evidence を要求するなら B にするべきです。その場合、「後段が最終回答を作る」ことは evidence を評価しない理由にはなりません。

### 2. 疑似コードの状態管理を完成させる

疑似コードの追加は大変よい改善です。ただし、実装に近い疑似コードだからこそ、状態変数の扱いを曖昧にしないほうがよいです。

まず `return ... , evidence` の `evidence` が、擬似コード内で一度も代入・累積されていません。各反復で `verdict.evidence_chunk_ids` を得た後、それを全周で和集合にするのか、最終周の結果だけを出すのか、同じ evidence が再度返った場合にどうするのかを決めてください。後段へ渡すものなら、通常は**全周の evidence を ****`chunk_id`**** ごとに累積し、重複除去する**仕様が分かりやすいです。

同様に、`verdict.paper_ids` は最終周だけを anchor にするのか、過去の周で確認済みとなった論文も残すのかが不明です。本文の「確認した論文を起点に広げる」という意図なら、過去を捨てない累積集合のほうが自然です。ただし、設計上あえて最終周だけを使うなら、その理由を明記すべきです。

```
verified_papers ← ∅
evidence ← ∅

for step in 0..2:
    ...
    verdict ← LLM_verify(question, papers)
    verified_papers ← verified_papers ∪ verdict.paper_ids
    evidence ← evidence ∪ verdict.evidence_chunk_ids
    if verdict.sufficient or step == 2:
        break
    subqueries ← LLM_refine(question, verdict.missing)

anchors ← [A[0]] ∪ verified_papers
return top50(rrf_AB(A, B)), evidence
```

上は設計例であり、必ず実装と一致させる必要があります。重要なのは、**全周累積か最終周のみかを仕様として固定すること**です。

### 3. 最大3周と LLM 呼出し回数の整合を取る

現状の疑似コードは、`step == 2` で `sufficient == false` の場合にも `LLM_refine` を実行してからループが終了します。これでは、実際には使われない再分解を1回呼ぶことになり、「最大3周で分解1回＋検証1回」という説明と微妙にずれます。

最終周では refinement を行わず終了する分岐を明示してください。これは小さな点ですが、LLM 呼出し数・コスト・停止条件の説明に直結するため、再現性を気にする査読者は確認します。

### 4. ランキング B の anchor 自己追加と複数anchor融合を、疑似コードにも書く

本文 §3.4(b) では、「anchor 自身を B の先頭に置く」ことが重要な設計として説明されています。しかし疑似コードでは `neighbors(a, n=100)` のみで、anchor 自身を追加する処理が明示されていません。

以下の三点を、本文または疑似コードで固定してください。

| 未確定に見える点 | 明記すべき仕様 |
| --- | --- |
| anchor 自身 | 各anchorのBリストを `[anchor] + neighbors(anchor)` とするのか |
| 複数anchor | anchorごとの3ソース近傍をすべて同じ重みでRRFするのか、anchor単位で一度融合してから融合するのか |
| 重複と空リスト | 同じ論文が複数anchorの近傍に出た場合の扱い、Bが空のときのA-onlyへのフォールバック |

とくに複数anchor時のRRFの単位は、候補が「複数のanchorに支持されたため上がる」のか、「同じsource内の同じ論文を一度しか数えない」のかを左右します。中心手法の一部なので、付録ではなく本文で明記する価値があります。

### 5. 擬似chunkの扱いを一貫させる

本文と付録では、論文単位 BM25 が返す擬似chunkは順位付けに寄与する一方、evidence や Verifier の入力には使えない、と説明されています。これは明確です。

しかし疑似コードでは、`fused[:pool_k]` を取ってから擬似chunkを除外しています。この操作だと、擬似chunkが上位に多くある場合に、rerankerへ渡す候補数が200未満になります。また、論文単位BM25によって押し上げられた論文に実チャンクを補うのか、実チャンクがない論文をランキング A に残すのか、が分かりません。付録Bの「実チャンクが1本も無い論文では擬似chunkを使う」とも、疑似コードの除外処理は緊張関係にあります。

次のどちらかを実装仕様として選び、統一してください。

| 方針 | 例となる処理 |
| --- | --- |
| reranker候補を常に `pool_k` 件に保つ | 擬似chunkを除外した後、次順位の実チャンクで埋め戻す。論文単位BM25で得たpaperには最良の実チャンクを解決して渡す |
| 擬似chunkを順位付け専用にする | 擬似chunkはAのpaper順位にのみ寄与させ、rerank・pool・Verifierには入れない。実チャンクが無い場合のpaperを最終候補に残す規則を別途定義する |

どちらでも構いませんが、現在のままでは「paper index の利点が下流にどう接続されるか」が曖昧です。

## 重要だが優先度が一段下がる改善点

### 6. 属性フィルタ後の切詰めを疑似コードに含める

§3.1の文章では、`fetch_k` 件を取得して属性フィルタをかけた後、`per_index_k` 件へ切ることが明記されています。一方、疑似コードは `attribute_filter` の直後にRRFへ渡しており、切詰めが書かれていません。

以下のように一行加えるだけで、`fetch_k` と `per_index_k` の関係が明瞭になります。

```
runs ← [top_k(attribute_filter(r, constraint), per_index_k) for r in runs]
```

Seed Expansion側の `runs2` にも同じ規則を適用してください。これは、属性フィルタ発火時だけランキングの候補数が変わるのかという疑問を解消します。

### 7. Verifier の失敗時に再分解へ渡す情報を定義する

§5.6 は「判定が使えないときは再試行せず、sufficient を偽として次の反復に進む」と説明しています。ただし、使えない判定には `missing` も存在しないはずです。すると、`LLM_refine(question, verdict.missing)` に何を渡すのかが不明です。

失敗時は、たとえば次のいずれかに固定してください。

| 失敗時の方針 | 含意 |
| --- | --- |
| `missing = null` を与え、一般的な別表現のサブクエリを生成する | 反復を継続できるが、目的の絞り込みは弱い |
| refinementを行わず、次の反復を打ち切る | 無意味なLLM呼出しを避けられるが、最大3周を使わない |
| 直前のsubqueryを維持し、別のSeed Expansionのみ行う | クエリ生成の非決定性を減らせる |

意図した挙動がどれであっても、本文と疑似コードに一文入れれば十分です。

### 8. 「候補50本を平らに使う」という運用をIntroductionで早く示す

§5.1 の最終構成選択の説明は、今回の改稿で最も重要な改善です。しかし、その前提である「後段は候補50本を順位で切らずに平らに使う」が初めて出るのが Results です。

これは、候補列の順位を出力する一方で集合被覆を最適化するという、論文全体の目的関数を決める重要条件です。§1.1の出力定義に、次の趣旨を1文加えるとよいです。

> 下流モジュールは上位50候補を順位で閾値化せず候補集合として利用するため、本稿では順位付き出力を保持しつつ、最終構成の選択では候補集合の被覆も重視する。

これにより、Introductionでの「順位融合」とResultsでの「@50集合被覆」の関係が一貫します。

### 9. 関連研究の引用は、投稿版では引用形式を完成させる

Related Work はかなり良くなりました。ただし §2 の注意書き「引用は未確定」や角括弧による仮引用は、最終稿には残せません。実際の書誌情報・引用キーに置き換える必要があります。

また、以下は最終確認を勧めます。

| 箇所 | 確認したいこと |
| --- | --- |
| Qwen3-Embedding / Reranker | モデルカードまたは公式技術報告の正確な名称・年・引用方法 |
| SPECTER2 | 「引用関係を教師にする」という説明が原典の訓練設定と正確に対応するか |
| Query2doc | 本稿の「LLM書換え」との類似点・差異を過大にしないか |
| scientific QA / scientific retrieval | LitTraceQAそのもののタスク論文、または最も近い科学文献QAを1〜数本追加できるか |

既存要素を正しく位置付けたうえで、「A/Bに分け、Bを質問適合性rerankerに通さず、論文単位で統合する」という差分を述べる現在の書き方は妥当です。

### 10. 「未完了」「実行中」「必須実験」は作業原稿には有用だが、投稿稿からは外す

§5.4b、§5.8、§6の「未完了」「実行中」「必須の追加実験」は、現時点での研究管理としてとても分かりやすいです。ただし、投稿版では二つに分けるべきです。

| 現時点の素材 | 投稿前にすること |
| --- | --- |
| 未完了ベースライン表 | 実験が完了したら通常の主結果表に統合する |
| 実行中の本番走行 | 完走後に結果を更新し、未完了表記を削除する |
| 必須実験リスト | 実施できたものはResultsへ、実施できないものだけは短いLimitationsへ残す |
| `⚠` 記号 | すべて通常の文章または脚注へ置換する |

特に「必須」と言い切った追加実験を未実施のまま残すと、査読者に「著者自身が主張の証拠不足を認めている」と受け取られます。完了前の原稿としては正しいですが、提出版に残さないほうがよいです。

## 結論

数値を除いて読む限り、今回の原稿は**論旨の骨格、透明性、方法の追跡可能性が明確に改善しています**。とくに、最終構成の選択を下流の候補50本利用という実運用に結び付けた点は、初見の査読者にとって納得感があります。

投稿前に最も重要なのは、Evidence の責務範囲を一貫させることと、疑似コードで宣言した手順・例外処理を実装仕様として完全に閉じることです。そこを整えれば、未実験の値がまだ残っているとしても、論文は「後から結果を埋めるだけの骨格」ではなく、方法と主張が自立した原稿になります。
