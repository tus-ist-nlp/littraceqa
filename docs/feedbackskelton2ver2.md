LitTraceQA 改稿版：再レビュー

総評

改稿は大きく改善されています。前回の主な懸念だった、論文の中心主張の不明瞭さ、ecr の過度な前面化、Reader と検証モジュールの役割混同、gold の解釈の断定、テストデータでの過剰な主張、開発集合への過適合リスクの不透明さは、いずれもかなり丁寧に処理されています。

とくに、冒頭の一文主張、Introduction の「診断→提案→主要結果→貢献」という流れ、Evidence Verifier を retrieval controller として定義した点、evidence 未注釈 gold という中立的な命名、cr を主評価・ecr を診断指標とした表、そして limitations の率直さは、初見の査読者が原稿を信頼して読み進めるために大きく効いています。

ただし、今回の改稿で最も目立つ新しい論点は、最終システムの位置付けです。主表では本システムが − 3部品 構成に対して @20 の公式指標・診断指標で劣り、@50 の公式 cr だけが改善しています。一方、論文の中心主張であるランキング B の決定的アブレーションは − 3部品 構成上でのみ行われています。したがって、査読者は次のように問うはずです。


「ランキング B は有効そうである。しかし、なぜ − 3部品 ではなく、@20 を下げる本システムが最終構成なのか。また、最終構成においても B の利得は成立するのか。」

この問いに答えられれば、論文の骨格はかなり強くなります。

最優先で解くべき残課題

1. 完全構成でのランキング B アブレーションを出す

§5.2 は、同一の検索結果と verifier 出力を固定して A/B 融合のみを切り替える、非常に良い決定的対照です。しかし、明記されているとおり、これは − 3部品 構成の上での比較です。本システムの結果は multi ecr@20 = 0.9080 であり、§5.2 の A+B 側の 0.9253 より低い値です。

このため、中心主張を「最終システムの性質」として読むことは現状では難しいです。まず、完全構成の実行ログを使って A のみと A+B を再構成する対照を追加してください。候補列の再構成だけで済むなら、LLM を再走行せずに確認でき、計算コストも比較的小さいはずです。

この結果がもし「完全構成でも B は効くが、三部品の副作用で@20は下がる」であれば、論文はむしろ面白くなります。複数の順位付け機構が干渉するという、現実的な発見として報告できます。

2. 「本システム」を最終構成と呼ぶ根拠を決める

§5.1 の表では、本システムは − 3部品 構成に対して、multi と total の @20 で劣ります。single cr@1 も下がります。改善は主に cr@50 にあり、ecr@50 は同値です。つまり、注釈付き gold の候補集合を増やしたわけではなく、深い順位で evidence 未注釈 gold を増やす一方、注釈付き gold の並びを悪化させた、という解釈です。

この結果を隠していないことは評価できます。ただし、査読者は「それなら、より単純で@20が高い構成を採用すべきではないか」と考えます。論文中で次のいずれかを明確に選んでください。

現状の数値だけで「三部品を入れた本システムが推奨構成」と読ませるのは難しいです。最終構成を減らすことは後退ではなく、研究上の結論を鋭くする選択です。

3. 外部・標準ベースラインと関連研究の実引用を加える

Related Work が設けられた点はよいですが、現状は「広く使われている」「古くから知られる」「確立した概念」と述べるだけで、文献がありません。EMNLP 論文としては、ここは必ず実際の引用に置き換える必要があります。

同時に、主結果は内部構成の比較だけでは不足します。主催者の基準系があるなら必須です。ない場合でも、少なくとも sparse、dense、hybrid、hybrid+rereanker、Aのみ、A+Bを一表に置くべきです。

4. 導入・結論では、慎重にした表現を最後まで保つ

§1.3 は改稿で非常に慎重になりました。しかし §6(6) と §7 では、再び「到達できない層が構造的に残る」「gold の約2割は質問文が言及せず」と強く書かれています。これは §1.3 の「注釈仕様との対応は未確認」「数件の内容確認に基づく」という留保と整合しません。

以下のように統一することを勧めます。

現在の表現

限定は弱さではありません。データセットの注釈規約が未確認である以上、限定した主張のほうが、査読者には正確で信頼できるものとして届きます。

5. Introduction の「主要な結果」は公式指標を先に置く

§1.5 は ecr@20 と注釈付き gold 基準の All-Gold@50 を前面に出しています。一方、§4.2 では cr が主評価と明記されています。両者の順番をそろえてください。

たとえば、最初に「公式 cr@20/@50」、次に「診断用 ecr@20」、最後に「All-Gold@50」を示すと自然です。また、ランキング B の 0.7356→0.9253 は − 3部品 構成上の数値なので、Introduction でもその条件を短く添えるべきです。条件を隠しているように見えるのを避けられます。

6. Method はさらに一段だけ、実装順序を固定する

3層図により全体像は大幅に読みやすくなりました。残る不明点は、属性フィルタの位置と件数です。§3.1 の図は論文単位RRFとSeed Expansionの後に属性フィルタがあるように見えますが、§3.2.4 は「各索引から多めに取ってから落とす」と読めます。per_index_k=100 と max_fetch_k=3000 の関係も分かりません。

また、チャンクプールから「上位20論文×2チャンク」を Evidence Verifier に渡す変換規則を明記してください。同一論文の複数チャンク、チャンクが2本ない論文、擬似チャンク、同点の扱いが分からないと、evidence 結果を再現できません。

本文に短い疑似コードを置くのが最もよい解決策です。

Plain Text


for each subquery:
    retrieve K candidates per index
    apply metadata filter and fallback
    fuse paper-level ranked lists
    optionally run Seed Expansion and fuse again
    rerank top P real chunks, then add top T chunks to the global pool

select 20 papers from the pool and up to two real chunks per paper
run the Evidence Verifier; stop or regenerate queries
aggregate the final pool to ranking A
retrieve and fuse paper-neighborhood rankings into B
fuse A and B, then return the top 50 papers and evidence



実際の実装と完全に一致するように調整したうえで、例外処理を一文ずつ添えれば十分です。

8. 用語と構成名を少しだけ整理する

「− 3部品」は、ランキング B 内の「3ソース」と視覚的に混同しやすいです。たとえば Base-A+B と Enhanced-A+B、または A+B (base) と A+B (three retrieval refinements) のように改めると、表を読む負担が減ります。

さらに §5.4 の BM25-only 結果は、論文単位BM25を最終構成に持つ根拠として用いられています。しかし完全構成上での追加効果は測っていません。この節は「縮約条件における索引粒度の分析」と明記し、完全構成での有効性まで主張しないほうが安全です。

本文・付録の配分は適切になっている

実装上のスコアオフセット、擬似chunk、protect_top、サブクエリ用プロンプト注記、未採用案を付録へ移した判断は正しいです。本文ではこれ以上、細かな開発経緯を増やさないでください。

論文としての現時点の判定

構成と主張の明瞭さは、前稿より明確に向上しています。 とくに、自身の限界を隠さず記す姿勢は好印象です。一方で、査読判断を左右しうる弱点は、単に Limitations に記載しただけでは解消しません。

最も重要なのは、ランキング B が完全構成でも効くか、そして @20を下げる三部品を含む構成を、なぜ最終システムに採用するのか の二点です。ここを結果で整理し、主張を公式指標・外部ベースライン・実際のコンペ評価に結び付けられれば、現在の改稿はかなり説得力の高い論文になります。
